04 · Addressing and ARP

Two types of addresses, and the bridge between them

Every device on the internet has two addresses — an IP address and a MAC address. Why both? And how does a machine find the MAC address of another when it only knows the IP address?

The IP address is a logical address. It depends on where you are located in the network — if you move your laptop from the university to your home, you get a new IP. Routers use IP addresses to send packets across the entire internet. But on the link itself — the last hop from the router to you, or between two hosts on the same switch — it is not the IP address that is used. There, a physical, hardwired address is needed: the MAC address.

A MAC address is 48 bits long, typically written in hexadecimal with hyphens: 1A-2F-BB-76-09-AD. It is (in theory) unique for every network interface card in the world — manufacturers are assigned address blocks by IEEE and burn the address into the ROM of the card. A good analogy: the IP address is like a postal address (changes if you move), the MAC address is like a national ID number (follows you).

On modern WiFi, the MAC address is often dynamic — iPhones and Android devices use a private, random MAC address per network to prevent tracking. The "burned-in" address is not always what you see.

Why do we need both?

Could we not just use IP all the way? In theory, but that breaks the layering. The link layer must be able to function without knowing anything about IP — on an Ethernet link, the packet inside might well be AppleTalk or IPX instead of IP. The link layer needs its own address type. And the MAC address has a practical property that IP does not: it is portable. You can move a network card between subnets without changing the MAC, but the IP must change.

The problem: IP does not know MAC

Here is the situation: host A wants to send an IP datagram to host B on the same LAN. A knows B's IP address (for example, from a DNS lookup). But to place the datagram in an Ethernet frame and send it on the cable, A needs B's MAC address. How does A find it?

The solution

ARP — Address Resolution Protocol. A tiny protocol that does exactly one thing: given an IP address on the same LAN, find the MAC address.

How ARP works

Each node has a small table (the ARP cache) with entries like <IP, MAC, TTL>. TTL is typically 20 minutes. When A wants to send to B:

  1. Is B already in the cache? Yes — use the stored MAC and send. Done.
  2. No? A creates an ARP query asking "Who has IP 137.196.7.14? Tell me."
  3. This message is encapsulated in an Ethernet frame with destination FF-FF-FF-FF-FF-FF — the broadcast address. Everyone on the LAN receives it.
  4. All hosts check: "Is that my IP?" All say no, except B, which replies with an ARP reply containing its MAC address. The reply is not broadcast — it is unicast directly back to A.
  5. A receives the reply, stores <B.IP, B.MAC, TTL=1200> in the cache, and can now send its original datagram.

What if the destination is not on the same LAN?

ARP only works within a single LAN — you cannot ARP your way to a server on the other side of the internet. If A wants to send to an IP that is in a different subnet, A does not send the frame directly to the destination host. Instead, A sends the frame to the first-hop router (default gateway). The frame has the router's MAC address as destination — but the IP datagram inside still has the final host's IP address as the target.

The router receives the frame, extracts the IP datagram, looks up in its routing table where the datagram should go next, encapsulates it in a new frame with new source and destination MACs (ARP on the next link), and forwards it. The IP addresses remain unchanged the entire way. The MAC addresses change at every hop.

Key insight

IP addresses are end-to-end. MAC addresses are hop-by-hop. The datagram's IP header sees the same addresses all the way from A to B. But the frame itself is re-encapsulated — with new MAC addresses — at every single router along the way.

If an attacker sends fake ARP reply messages on a LAN claiming to have the IP address of the default gateway router, what happens?
This is ARP spoofing (or ARP poisoning) — a classic Man-in-the-Middle attack. The victims' ARP tables are poisoned with the attacker's MAC address, and all packets intended for the "router" are instead sent to the attacker, who can read them and optionally forward them to the real router. ARP has no authentication — that was not part of the design in the 1970s. That is why ARP spoofing is used by both attackers and security researchers.
05 · Ethernet

The victorious LAN technology

Ethernet was invented by Robert Metcalfe in the 1970s. It should have died out long ago — competitors were more sophisticated, faster, better designed. But Ethernet outlived them all. Why?

The answer: simplicity and low cost. Ethernet was never the most technically refined solution, but it was "good enough" and very easy to implement. While Token Ring and ATM struggled with complex protocols, Ethernet scaled from 10 Mbit/s up to 400 Gbit/s without fundamentally changing the frame structure or addressing system. Today, Ethernet is the dominant wired LAN technology — and has been for several decades.

From bus to star

Originally, Ethernet was a bus technology: all machines were connected to one long coaxial cable, and everyone heard everything. Collisions were common — hence CSMA/CD. This worked, but it gave one collision domain for the entire network, and the bandwidth was shared among all.

Modern Ethernet is switched: each host has its own dedicated cable to a central switch. Each link is a separate collision domain with only two endpoints — the host and the switch. Collisions become practically impossible, and full-duplex is the standard: both sides can send simultaneously without interfering with each other. CSMA/CD still exists in the specification, but it is activated only in rare cases where a host goes into half-duplex mode.

The Ethernet frame

Let us look at each field:

  • Preamble (8 bytes). Seven bytes of 10101010 followed by one byte of 10101011. Used to synchronize the receiver's clock with the sender's — the last two bits "11" signal that the frame starts now.
  • Destination MAC (6 bytes). Who should receive it. If the NIC sees its own address (or the broadcast FF-FF-FF-FF-FF-FF), it delivers the contents up to the network layer. Otherwise, the frame is discarded.
  • Source MAC (6 bytes). Who sent it.
  • Type (2 bytes). Which protocol is inside? 0x0800 = IP, 0x0806 = ARP, etc. The receiver's NIC uses this to demultiplex upward — the correct protocol at the network layer gets the packet.
  • Data (46–1500 bytes). The payload. Minimum 46 bytes — shorter packets must be padded — because CSMA/CD needs a minimum length to detect collisions. Maximum 1500 bytes is the MTU limit (Maximum Transmission Unit).
  • CRC (4 bytes). CRC-32 over the entire frame. Error → the frame is discarded immediately.

Unreliable and connectionless

Ethernet is connectionless: there is no handshake between the NICs before data is sent. And it is unreliable: the receiver does not send an ACK on success and no NAK on error — it simply discards frames with errors. If data is lost, it is up to higher layers (TCP) to detect and retransmit. This is entirely deliberate. On modern wired links, the error rate is so low that end-to-end reliability is far more efficient than per-hop reliability.

06 · Switches

The humble, invisible hero

If you have an Ethernet LAN today, you have at least one switch. They are "plug-and-play," teach themselves, and hosts don't even know they exist. The magic lies in how they discover where things are.

A switch is a link-layer device — layer 2 — that forwards frames based on MAC addresses. It receives a frame on one port, looks at the destination MAC, and sends the frame out only on the single port where it knows the recipient is located. All other ports remain untouched. This means that multiple pairs of hosts can communicate simultaneously without interfering with each other. A switch with six ports can have three independent conversations going on at once.

Switches are transparent: hosts do not see them. You do not need to configure the host to talk through a switch. You don't need to configure the switch either — it teaches itself. Plug in, and it works. This "plug-and-play" property is one of the main reasons switches displaced hubs and old bus networks.

The switch table

The heart of the switch is the forwarding table. Each entry is a triple (MAC address, port, timestamp). It tells the switch: "The host with this MAC address is reached via this port, and I learned this at this time." The timestamp lets old entries expire — if a host has been silent for a long time (typically a few minutes), it is deleted from the table.

How the switch learns — the self-learning algorithm

The switch starts with a completely empty table. When it receives a frame:

  1. Learn. Look at the source MAC and the port the frame arrived on. Store this mapping in the table (or update the timestamp if it already exists).
  2. Look up. Look at the destination MAC. Is it in the table?
  3. If yes: If the destination is on the same port the frame arrived from — discard it (the recipient has already heard it). Otherwise, forward it only on the port where the recipient is.
  4. If no: Flood. Send the frame out on all ports except the one it arrived on. The recipient will reply, and then the switch learns where the recipient is.
Note that the switch learns only from source addresses — never from destination addresses. This is because the source address is verified ("whoever sent the frame obviously came from that port"), while the destination is merely a hope about where the frame should go.

Interconnecting switches

Self-learning works exactly the same when multiple switches are connected together in a tree hierarchy. Each switch learns on its own, through its own ports, which direction a given MAC address lies. If host A on the far left wants to send to host G on the far right, the first switch floods the frame out, and along the way all switches learn where A is (because they see the source MAC). When G finally replies, all switches learn where G is (from G's source MAC in the reply). After one round-trip exchange, the route is fully established, and future frames are sent directly.

Switches vs. routers

This often causes confusion. Both switches and routers are "store-and-forward" devices — they receive a packet, think, and forward it. But they operate at different layers and with different addresses.

07 · Synthesis

A day in the life of a web request

Now we tie everything together. A student connects a laptop to the university network and opens google.com in the browser. It seems simple. Let's see how many protocols are actually set in motion.

The scenario is this: a new laptop connects to a wired Ethernet on campus. The user types www.google.com in the browser and presses Enter. We trace everything that happens — from the moment the cable is plugged in, to the first pixel of the Google logo appearing on the screen.

Step 1 — Get an IP address with DHCP

Before the laptop can send anything out on the internet, it must have an IP address. It also needs to know the IP address of the first-hop router (default gateway) and the IP address of a DNS server. DHCP (Dynamic Host Configuration Protocol) solves all of this.

The laptop creates a DHCP request, encapsulates it in UDP, then IP, then an Ethernet frame. The destination MAC is FF-FF-FF-FF-FF-FF — broadcast — because the laptop does not know who the DHCP server is yet. The frame is flooded through the LAN to the router (which runs the DHCP server). It replies with the laptop's new IP address, subnet mask, default gateway, and DNS server. After this single exchange, the laptop has everything it needs to be on the network.

Step 2 — Find the router's MAC with ARP

The laptop will eventually need to reach a server outside its own LAN. All such packets must go through the router. To send the first frame to the router, the laptop needs the router's MAC address. It only has the IP address from the DHCP response.

ARP solves this. The laptop broadcasts: "Who has IP 68.80.2.1?" The router replies with its MAC. Now the laptop is ready.

Step 3 — Find Google's IP with DNS

The user typed www.google.com, not an IP address. The laptop must convert the name to an IP. It creates a DNS query, encapsulates it in UDP / IP / Ethernet, and sends it toward the default gateway. The frame has the router's MAC as destination, but the IP datagram inside has the DNS server's IP as the target.

The router receives the frame, extracts the IP datagram, looks up in the routing table (built by protocols like OSPF and BGP), and forwards it toward the DNS server — typically through the ISP's network. The DNS server replies with Google's IP address, for example 64.233.169.105. The reply takes the return path through multiple routers and eventually arrives back at the laptop.

Notice how the IP addresses in the IP header remain stable the entire way — they are source and destination end-to-end. But the MAC addresses change at every router. Each hop has its own frame, each with new MACs.

Step 4 — Set up the TCP connection

Now the laptop knows Google's IP. The browser opens a TCP socket and starts the three-way handshake: SYN → SYNACK → ACK. Each of the three messages travels as a separate IP datagram, encapsulated in Ethernet frames at each hop, through perhaps 15 routers across the internet. When the handshake is complete, there is a reliable TCP connection between the laptop and Google's server.

Step 5 — HTTP request and response

The browser writes an HTTP request into the TCP socket: GET / HTTP/1.1. It is divided into segments by TCP, each segment becomes an IP datagram, each datagram becomes a frame at each hop. Google's server receives the request, generates the HTML response, and sends it back through the same TCP connection. The browser parses the HTML, requests images and stylesheets (more HTTP requests), renders the page — and finally the user sees the Google logo.

The big takeaway

What looks like a single action — "open a web page" — actually involves seven different protocols working together: DHCP, ARP, DNS, IP, TCP, Ethernet, and HTTP. Each of them solves one specific problem. None of them could do the job alone. And thanks to layering, none of them knew the others existed. That is what the internet is.
