05 · Secure email

Secure email

Three goals: confidentiality, integrity, and authentication — and Alice uses three different keys to achieve them all.

Email is the perfect example for putting together all the "puzzle pieces" we have learned so far. Imagine that Alice wants to send an email to Bob that is (1) confidential — only Bob can read it, (2) authenticated — Bob can verify that Alice wrote it, and (3) integrity-checked — the content cannot be altered en route. Let us build the solution step by step.

Step 1: Confidentiality only

Alice could encrypt the entire message with Bob's public key, but that is far too slow for a long email. Instead, she does something clever:

  1. Generate a random symmetric session key KS
  2. Encrypt the message with KS (fast, using e.g., AES)
  3. Encrypt KS with Bob's public key KB+ (slow, but KS is short)
  4. Send both KS(m) and KB+(KS) to Bob

Bob uses his private key to decrypt KS, and then uses KS to decrypt the message itself. This is hybrid encryption — the best of both worlds.

Step 2: Integrity and authentication only

Sometimes the message does not need to be secret, but the receiver should be able to verify who sent it. Alice computes H(m), signs the hash with her own private key KA−, and sends both the message (in plaintext) and the signature KA−(H(m)). Bob verifies with Alice's public key.

Step 3: All together

For full security, Alice combines the two techniques. She uses three keys:

Alice's three keys for secure email

1. KA− (Alice's private key) — signs H(m) for integrity and authentication.

2. KS (random symmetric session key) — encrypts the message + signature for confidentiality.

3. KB+ (Bob's public key) — encrypts KS so that only Bob can decrypt.

Bob performs the complementary operations in reverse order: decrypt KS with his private key, decrypt the message with KS, verify the signature with Alice's public key.

06 · TLS

TLS: securing TCP connections

The most widely deployed security layer on the Internet — what makes HTTPS possible.

Transport Layer Security (TLS) is the protocol that adds a security layer on top of TCP. When you see the padlock in the browser and "https" in the URL, it is TLS working under the hood. TLS provides the three classic properties — confidentiality (via symmetric encryption), integrity (via cryptographic hashing), and authentication (via public key cryptography and certificates) — using all the techniques we have already learned.

Where does TLS sit in the protocol stack?

TLS is not a separate layer in the traditional sense — it is a sublayer that sits between TCP and the application layer. The application (e.g., a browser) writes data to a "TLS socket" instead of a regular TCP socket. TLS encrypts the data and sends it down to TCP as ordinary TCP segments. To TCP and IP below, everything looks normal — they do not know the content is encrypted.

Key derivation

After the handshake, Alice and Bob share a "master secret". But it is considered bad practice to use one key for everything. Therefore, they derive four separate keys from the master secret:

  • EA — encryption key for data from Alice to Bob
  • EB — encryption key for data from Bob to Alice
  • MA — MAC key for data from Alice to Bob
  • MB — MAC key for data from Bob to Alice

Record-based encryption

TCP provides a byte stream, but TLS cannot encrypt the stream continuously — because then the MAC would only come at the end, and the receiver could not check integrity until the entire connection closes. The solution: TLS divides the stream into records. Each record contains data, a MAC for integrity, and a length. The entire record is encrypted with the session key before being sent to TCP.

An important point: the MAC is not computed over just the data in the record — it also includes a sequence number. Even though the sequence number is not sent explicitly in the record, both parties maintain an internal counter. Without sequence numbers, Trudy could capture a record and replay it (replay attack), or rearrange the order of records without the receiver noticing. With the sequence number in the MAC computation, any such manipulation will cause the MAC verification to fail.

TLS 1.3 and cipher suites

A "cipher suite" is a set of algorithms used together: one for key exchange, one for encryption, one for MAC, and one for digital signature. TLS 1.3 (RFC 8446, 2018) is the latest version and has significantly tightened the choices.

In TLS 1.3, AEAD (Authenticated Encryption with Associated Data) is often used: encryption and integrity in one operation, instead of older designs with a separate MAC over the payload. Record layout and the need for integrity and replay protection still follow the same principles as in the simplified "toy TLS" explanation above.

07 · IPsec

IPsec and VPN

Security at the network layer — where entire IP datagrams are encrypted and authenticated.

TLS secures individual transport connections (one TCP connection at a time). But what if you want to secure all traffic between two networks — regardless of application, regardless of port? Then you need security at the network layer, and that is where IPsec comes in. IPsec provides encryption, authentication, and integrity checking at the datagram level, for both user data and control traffic (BGP, DNS, etc.).

Security Association (SA)

Before IPsec can send a single encrypted datagram, the two endpoints must establish a Security Association (SA) — a one-way logical connection that defines the security parameters for the traffic. Each SA is identified by three things:

  • SPI (Security Parameter Index): a 32-bit number included in every IPsec datagram, so the receiver knows which SA (and thus which keys and algorithms) the packet belongs to.
  • Destination IP: the address of the other end of the SA.
  • Protocol identifier: whether the SA uses AH or ESP.

Because an SA is one-way, two SAs are needed for bidirectional communication — one in each direction, each with its own SPI and its own keys. All active SAs are stored in a SAD (Security Association Database) on both endpoints. When an IPsec datagram arrives, the receiver uses the SPI value in the header to look up the correct SA in the SAD and thus find the encryption key and algorithm needed to decrypt.

SPD — which traffic should use IPsec?

Besides the SAD, each endpoint has an SPD (Security Policy Database): a set of policy rules that say which packets (e.g. by source/destination subnet, protocol, or port) must be processed by IPsec, and whether they should be dropped, sent in the clear, or tunneled/encrypted with a particular SA. In short: the SPD decides whether IPsec applies; the SAD says how (keys and algorithms for an active SA).

Two modes

ModeWhat is encryptedUse
Transport Only the payload of the IP datagram Between two endpoints (host-to-host)
Tunnel The entire original datagram, encapsulated in a new one Between two gateways (VPN) — most common in practice

Tunnel mode is the foundation for VPN (Virtual Private Network). Consider a company with offices in Oslo and Trondheim. Both offices are connected to the Internet, and between the gateway routers at each office, an IPsec tunnel is set up. All traffic between the two office networks is encapsulated in encrypted IP datagrams and tunneled over the public Internet. To the user's PC, it looks as if it is on the same local network — but in reality, everything is encrypted in transit.

Two protocols

ProtocolAuthenticationIntegrityConfidentialityUse
AH Yes Yes No Rarely used alone
ESP Yes Yes Yes Most used — provides everything

ESP is by far the most used of the two — it provides all three properties. AH provides only authentication and integrity (but no encryption), and is rarely used alone in modern networks.

IKE — when and how SAs are created

A Security Association describes which keys and algorithms to use — but the SA must be established first. IKE (Internet Key Exchange, today IKEv2) is the protocol that runs between the IPsec endpoints (hosts or gateways) to negotiate and install those SAs securely.

In brief: the parties authenticate each other (e.g. with a shared secret, digital certificates, or both), exchange or derive key material (often with Diffie–Hellman-like steps for perfect forward secrecy), and agree which IPsec SAs (SPI, algorithms, lifetime) to insert into the SAD. Without IKE, an administrator would have to configure keys manually — impractical and risky at scale.

So the VPN tunnel from the previous paragraph does not merely "encrypt IP"; it relies on IKE first establishing the concrete ESP or AH SAs that the data packet later refers to via the SPI.

08 · Wireless security

Security in wireless networks

How WiFi (802.11) and mobile networks (4G/5G) authenticate devices and encrypt traffic over the air.

Everything we have seen so far — encryption, signatures, CAs — are general mechanisms. But wireless networks have a special need: the device connecting must authenticate itself before it gets any access to the network at all, and all traffic over the air must be encrypted because radio waves are trivially easy to eavesdrop on. Let us see how WiFi and 4G/5G solve this.

From WEP to WPA3

The WPA3 handshake in detail

Step 2 (mutual authentication and key derivation) is the most interesting. In WPA3, it works as follows:

  1. AS sends NonceAS — a random one-time-use number — to the mobile device.
  2. The mobile device generates NonceM, derives a symmetric session key KM-AP from both nonces, the pre-shared password, and the MAC addresses, and sends NonceM plus an HMAC value (authentication code derived with the secret keying material — not a digital signature in the PKI sense) back.
  3. AS derives the same KM-AP using the same ingredients, verifies the HMAC, and both parties now have a shared session key — without the password ever having been sent over the air.
HMAC (Hash-based Message Authentication Code) is a symmetric MAC: hash plus shared secret material (RFC 2104). It confirms integrity and that the peer knows the same secret basis as in the handshake.

4G LTE: authentication with SIM cards

Mobile networks are fundamentally different from WiFi because the identity resides in the SIM card, not in a password. The SIM card contains a globally unique identifier (IMSI) and a pre-shared secret key KHSS-M that only the SIM card and the home network's HSS (Home Subscriber Server) know.

The authentication flow in 4G involves several actors:

ComponentRole
UE (mobile device)Contains the SIM with IMSI and pre-shared key
eNode-B (base station)Relays authentication messages
MMEMakes the authentication decision in the visited network
HSSUltimate authority — knows all subscribers and their keys

Authentication flow (simplified)

  1. a) The mobile sends an attach message with IMSI via the base station and MME to the HSS in the home network.
  2. b) The HSS uses the pre-shared key KHSS-M to compute an auth_token and an expected response xresHSS. The auth_token contains encrypted information that only the mobile device can verify. The HSS sends both to the MME.
  3. c) The MME forwards the auth_token to the mobile. The mobile verifies the auth_token with its own key — and thus knows the network is genuine. The mobile computes its own response resM and sends it back.
  4. d) The MME compares resM with xresHSS. If they match, the mobile is authenticated. The MME informs the base station and generates session keys.
  5. e) The mobile and base station derive encryption keys KBS-M to encrypt all further communication over the 4G link (typically with AES).

From 4G to 5G: key changes

4G LTE5G
Authentication decisionMME in visited networkHome network
Key typePre-shared keysAlso supports keys for IoT

The most notable improvement in 5G is that the IMSI is now encrypted — in 4G it was sent in plaintext, which enabled IMSI catchers (fake base stations that capture mobile identities).

09 · Operational security

Firewalls

The first line of defense between the internal network and the wild Internet.

Cryptography protects the content of communication, but that is not always enough. An organization also needs to control which traffic is allowed in and out of the network at all. That is the job of a firewall: it sits between the organization's internal network and the public Internet, filtering packets based on a set of rules.

Why a firewall?

  • Prevent DoS attacks: e.g., SYN flooding where an attacker fills up the server's connection resources with fake TCP requests.
  • Prevent unauthorized access: block access to internal services that should not be exposed to the Internet.
  • Allow only authorized traffic: restrict access to a set of approved users, protocols, and ports.

Three types of firewalls

1. Stateless packet filtering

The simplest form: the firewall examines each packet in isolation and decides whether to let it through or drop it, based on information in the header:

  • Source and destination IP address
  • Source and destination port number (TCP/UDP)
  • ICMP message type
  • TCP SYN and ACK flags

The rules are expressed in an Access Control List (ACL) — a table where rules are checked from top to bottom, and the first match decides:

Filtering examples

Block all incoming UDP: drop all packets with IP protocol field = 17. Result: no UDP traffic (e.g., DNS queries from outside) gets in.

Block all Telnet: drop all TCP segments with destination port 23. Result: no one can establish Telnet connections to internal machines.

Block incoming TCP connections: drop incoming TCP segments with ACK=0. Result: external clients cannot initiate TCP connections inward, but internal clients can connect out.

2. Stateful packet filtering

The problem with stateless filtering is that it is too coarse-grained. It lets through packets that "look right" but do not belong to any real connection — e.g., a packet with the ACK flag set that appears to be a response, but no request was ever sent.

A stateful firewall solves this by keeping track of all active TCP connections. It tracks setup (SYN), teardown (FIN), and timeout for inactive connections. An incoming packet is only let through if it belongs to a connection that has already been set up in the connection table.

3. Application gateway

An application gateway does not just filter on IP/TCP headers, but also inspects application data. For example: only selected internal users are allowed to use Telnet. All Telnet connections must go through the gateway, which verifies the user identity before setting up a forwarded connection to the final destination.

Limitations

Firewalls are no magic solution:

  • IP spoofing: the router cannot verify that the source IP is genuine.
  • Scalability: each application that needs special treatment requires its own gateway.
  • All-or-nothing for UDP: difficult to distinguish "good" from "bad" UDP traffic.
  • Trade-off: the stricter the filtering, the more legitimate communication is also restricted.
