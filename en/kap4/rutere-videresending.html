01 · Overview

What the network layer does

The transport layer gives you the illusion of a direct connection between two processes. The network layer is the one that actually has to move packets across a multitude of different networks to maintain that illusion.

The network layer runs in every single Internet-connected device — not just in routers, but also in end systems. On the sender side, it receives segments from the transport layer, encapsulates them in datagrams, and delivers them to the link layer below. On the receiver side, it does the reverse: extracts the segment from the datagram and delivers it up to the transport layer.

But the real work happens in routers. A router examines the header fields in every single datagram that passes through it, and determines — in nanoseconds — which output port the packet should be forwarded on. This process is repeated router after router until the packet reaches its destination.

★ Everything over IP, IP everywhere

The network layer has only one protocol: IP. All transport protocols (TCP, UDP, QUIC) run over IP, and IP runs over all link-layer technologies (Ethernet, WiFi, 5G). This simplicity — a single narrow waist — is the Internet’s most important design decision.

02 · Forwarding vs. Routing

Two entirely different jobs

Forwarding is what you do at each intersection: «given that the destination is Rome, I turn right.» Routing is planning the entire trip from Trondheim to Rome before you get in the car.

The distinction between forwarding and routing is the first real insight of this chapter, and the rest of the material is organized around it.

Forwarding is the local, per-packet operation: a router receives a datagram on an input port, looks up the destination address in a forwarding table, and sends the packet out on the correct output port. This must happen extremely fast — in nanoseconds — because a 100 Gbps link does not wait for anyone.

Routing is the network-global process that determines which routes exist in the network, and that populates the forwarding table with entries. Routing algorithms (OSPF, BGP) run in the background and update the tables when the topology changes. Routing is slow — milliseconds to seconds — but that is fine, because it happens infrequently compared to forwarding.

03 · Data plane & Control plane

Two planes in a router

The same forwarding/routing distinction manifests itself as an architectural division inside any modern router: the data plane for fast packet movement, the control plane for routing logic.

Data plane is the hardware that actually moves packets from input port to output port. It operates in nanoseconds, with dedicated circuits performing table lookups and switching without involving the router’s CPU.

Control plane is the software that determines what should be in the forwarding table. In the traditional model, each router runs its own routing logic and exchanges reachability information with neighbors using protocols such as OSPF and BGP, then installs the resulting entries in its forwarding table.

04 · Service model

Why the Internet is so «dumb»

One could imagine a network that guarantees delivery, bandwidth and low delay. The Internet does none of these things. It is «best effort» — and that is by design.

The Internet’s network layer promises nothing. No guarantee that the packet will arrive. No guarantee of ordering, timing, or bandwidth. The IP model is best effort: we try to deliver your packet, but we promise nothing.

This stood in sharp contrast to the ATM networks developed in the 1990s, which attempted to provide rich guarantees. But history proved the Internet right:

Three things explain why best effort works:

  • Simplicity scales. Routers that just look up a destination and forward can be built cheaply and quickly by anyone.
  • Overprovisioning works. Bandwidth has become cheap enough that real-time applications like video and voice work «well enough, most of the time.»
  • CDNs and congestion control help. Content is replicated near users, and TCP prevents the network from collapsing.

Why did the Internet choose «best effort» over a richer service model like ATM CBR?

Correct! Simplicity is the core reason. A router that only needs to look up a destination address and forward the packet can be built cheaply by anyone. Guarantees require per-flow state and resource reservation in every router, which hinders growth.
05 · Inside a router

The anatomy of a router

A router consists of four main components: input ports, a switching fabric, output ports, and a routing processor. The first three are data plane; the fourth is control plane.

An input port does three things before a packet moves on. First, line termination (receiving bits from the fiber). Then, link-layer processing (assembling bits into Ethernet frames). Finally, the critical step: looking up the forwarding table to determine the output port. This last step happens locally in the input port, without involving the CPU.

The lookup is a fast prefix/destination match: read the destination IP (typically), find the longest matching prefix in the forwarding table, and send the packet out on the indicated interface. That is traditional destination-based IP forwarding in the data plane (as in this course, excluding generalized forwarding / SDN in textbook section 4.4).

06 · Longest Prefix Match

Which entry wins?

The forwarding table contains prefixes, not individual addresses. When multiple prefixes match, the longest one wins — because a longer prefix is more specific.

A forwarding table typically has a quarter of a million entries. Each entry is a prefix — for example 200.23.16.0/20 — that covers all addresses where the first 20 bits match. The big question is: what does the router do if a destination address matches multiple entries?

The answer: select the entry with the longest prefix. A /24 covers 256 addresses; a /28 covers only 16. If both match, /28 is more precise and wins. This is longest prefix matching (LPM), and it is what makes hierarchical addressing and route aggregation possible.

In practice, LPM is performed in hardware, using ternary content-addressable memory (TCAM). A TCAM looks up an address in a single clock cycle regardless of table size, because all entries are compared in parallel. Cisco Catalyst switches have around 1 million entries in TCAM.

A router has the entries 10.0.0.0/8 → port 0 and 10.1.0.0/16 → port 1. Where is a packet to 10.1.5.3 sent?

Correct! Both prefixes match the address, but /16 is more specific than /8. Longest prefix matching always selects the most specific match.
Why is forwarding implemented in hardware (ASIC/TCAM) rather than software?
A 100 Gbps link delivers a 64-byte packet roughly every 5 nanoseconds. Software on a general-purpose CPU cannot perform a table lookup that quickly. That is why purpose-built circuits (ASICs) and TCAM are used, which can look up among hundreds of thousands of prefixes in a single clock cycle — independent of table size. Without hardware acceleration, routers would become the bottleneck of the Internet.
07 · Switching fabric

The three generations

Once the input port has determined the output port, the packet must be physically moved there. The switching fabric does this, and there are three main designs — an evolution from slow to extremely fast.

Generation 1: via memory. The packet is copied from the input port to system memory, the CPU performs the lookup, and the packet is copied to the output port. Two bus crossings per packet — speed is limited by memory bandwidth. Worked for a few megabits per second.

Generation 2: via bus. Packets are transferred directly from input port memory to output port memory over a shared bus, without CPU involvement. But the bus is shared — bus contention — so only one packet can cross at a time. The Cisco 5600 uses a 32 Gbps bus.

Generation 3: interconnection network. A crossbar or multi-stage switch allows multiple packets to cross in parallel, as long as they are going to different output ports. For even higher throughput, modern routers split packets into cells and send them over multiple parallel fabric planes simultaneously. Cisco CRS: 8 planes, hundreds of Tbps.

08 · Queues, buffers & scheduling

When packets must wait

Even with a perfect switching fabric, queues form. What happens in the queues — who gets dropped and who goes first — is where network neutrality gets its technical substance.

Input queues and HOL blocking

If the switching fabric is slower than the sum of the input ports, queues can build up at the input ports. The worst thing that then happens is Head-of-Line (HOL) blocking: the packet at the front of the queue is waiting for a busy output port, and thereby blocks the packets behind it — even if their output ports are free.

Output queues

The most common queue type is at the output port. When three input ports at 10 Gbps all want to send to the same output port, something must wait. Here two questions arise: (1) what is dropped when the queue is full? (2) which packet is sent first?

Buffer sizing

An old rule of thumb (RFC 3439) states that the buffer should be approximately RTT × C (for example, 250 ms × 10 Gbps = 2.5 Gbit). More recent research recommends RTT·C / √N where N is the number of flows — because overly large buffers create bufferbloat and ruin latency for real-time traffic.

Buffer management

Tail drop: drop the packet that just arrived. RED (Random Early Detection): drop packets randomly before the queue is full to signal congestion earlier. (ECN-based marking instead of drops is tied to textbook sections not included in TTM4100.)

Weighted Fair Queueing (WFQ) generalizes round robin by giving each class a weight wi, such that class i receives the share wi / Σwj of the link capacity. This is how you can guarantee minimum bandwidth to a given traffic type without starving the others.

Network neutrality — technically speaking

FCFS is «neutral.» Priority scheduling based on paying customers is «paid prioritization» — what the 2015 FCC rules prohibited. Scheduling and buffer rules are the mechanisms where net neutrality policy takes on technical substance.

What happens to latency if the buffers in a router are too large?
Bufferbloat. With overly large buffers, fewer packets are dropped, so the loss rate looks good — but packets sit in the queue for a long time before being forwarded. The result is high and variable latency that ruins interactive applications (VoIP, gaming, video conferencing). TCP does not detect the loss soon enough and does not reduce its window, so the queues remain full. More recent research recommends RTT·C / √N instead of the old RTT·C rule, precisely to avoid bufferbloat.
