How the Internet talks: email, names, and sockets

A thorough walkthrough of three of the application layer's most important building blocks — the protocols that move your email, translate names to addresses, and let processes communicate across the globe.

01 · Email and SMTP

The oldest messaging service on the network

Email existed before the web, before Facebook, before practically everything. When you understand how an email actually travels from you to the recipient, you also understand why the entire application layer is built around a small set of recurring patterns.

Let us begin with a question that sounds trivial but is not: when you press "Send" in Gmail, what actually happens? You know the message ends up with the recipient — but between "press" and "delivered" lies an entire little ecosystem of software, and it is that ecosystem we are now going to unpack.

The email system consists of three main components. There is the client program you use to read and write — called the user agent or "mail reader." There are the mail servers that actually store messages, both in an inbox for what comes in and in an outgoing queue for what needs to be sent. And then there is SMTP, the protocol that binds the servers together and moves messages between them.

The important thing to realize is that the user agent never talks directly with the recipient's user agent. Your mail first ends up at your mail server, which then opens an SMTP connection to the recipient's mail server and delivers it. The recipient then picks it up from their own server using an entirely different protocol. This is not a coincidence — it is a deliberate design that we will soon see why is smart.

Notice a fundamental asymmetry here: SMTP is used only between the servers (and from Alice's user agent in to her own server). When Bob reads his mail, he does not use SMTP. He uses a "mail access protocol" — typically IMAP, or HTTPS if he uses Gmail in the browser. Why? Because SMTP is a push protocol: the sender takes the initiative and pushes the message forward. But when Bob wants to fetch mail, he wants to pull messages down from his own server. That is an entirely different usage pattern, and it requires an entirely different protocol.

SMTP dates from 1982 (RFC 821, updated to RFC 5321). That it is still in use, more or less unchanged, says something about how well it solved its problem — and how difficult it is to replace established protocols.

SMTP — a conversation in plaintext

SMTP is a TCP-based protocol on port 25. It is remarkably simple: commands are sent as ASCII text, and the server responds with a three-digit status code followed by a short text. The entire conversation between two mail servers looks like this:

SMTP conversation — step by step
S: 220 hamburger.eduC: HELO crepes.frS: 250 Hello crepes.fr, pleased to meet youC: MAIL FROM: <alice@crepes.fr>S: 250 alice@crepes.fr... Sender okC: RCPT TO: <bob@hamburger.edu>S: 250 bob@hamburger.edu ... Recipient okC: DATAS: 354 Enter mail, end with "." on a line by itselfC: Do you like ketchup?C: How about pickles?C: .S: 250 Message accepted for deliveryC: QUITS: 221 hamburger.edu closing connection

This is the entire protocol in a nutshell. Three phases: handshaking (HELO), transfer (MAIL FROM, RCPT TO, DATA), and closure (QUIT). The client — which is the sending mail server here — writes commands, the server responds with status codes. 250 means OK, 354 means "continue," 220 and 221 are opening and closing. Just like HTTP, but older.

A small but important detail: notice that the message body is terminated by a line containing only a single period. This is SMTP's way of saying "the message ends here." More precisely, the server looks for the sequence CRLF.CRLF to find the end of the message content. And because everything must be 7-bit ASCII, all binary content (images, attachments, special characters) must first be re-encoded to ASCII using MIME encoding.

Check your understanding
Why does email use two different protocols (SMTP and IMAP) instead of just one?
SMTP is designed for the sender to push a message forward to the recipient's server. When the recipient later wants to fetch their mail — perhaps from a mobile phone, perhaps later today, perhaps from multiple devices — that is an entirely different need. IMAP solves that problem: access to a mailbox stored on a server.

SMTP vs HTTP — so similar, yet so different

It is tempting to look at SMTP and HTTP and think they are almost the same thing. Both use TCP. Both have ASCII commands and status codes. Both were built in the same era. But the differences reveal two fundamentally different design philosophies:

PropertyHTTPSMTP
InitiativePull (the client requests)Push (the sender pushes)
ContentEach resource in its own responseMultiple objects in one multipart message
Character setBinary allowedRequires 7-bit ASCII
ConnectionPersistent (HTTP/1.1+)Persistent
Use caseFetching pages/data on demandDelivering messages asynchronously

These differences are not arbitrary. They follow directly from the problems the protocols solve. When you fetch a web page, you are there right now, waiting for the response. When you send email, the recipient might read it two days later — so the message must be queued, stored temporarily, and delivered when convenient.

The message format — RFC 822

SMTP is the protocol that moves the message, but the message itself — what lies inside the DATA block — has its own format defined in RFC 822. The comparison is roughly like HTTP and HTML: HTTP transports, HTML is what is transported.

An email message consists of header lines (To:, From:, Subject:, and so on), a blank line, and a body. It is important to distinguish these headers from the SMTP commands MAIL FROM and RCPT TO — the latter are part of the negotiation between servers (roughly like an envelope), while the RFC 822 headers are part of the letter itself inside the envelope. They often contain the same addresses, but they do not have to. (It is precisely this gap that some types of phishing exploit.)

How modern webmail actually looks

In practice, your traffic does not look exactly like the textbook. When you use Gmail or Outlook on the web, it is not SMTP that you speak from your browser to the server — it is HTTPS. Only when Gmail's servers need to deliver the message onward to the recipient's server does SMTP come into play. And when the recipient — also on the web — reads it, it is once again HTTPS all the way to the browser.

Summary
Webmail = HTTPS from you to your server, SMTP between servers, HTTPS from the recipient's server to the recipient. Traditional email client (Outlook, Apple Mail) = SMTP from you out, SMTP between servers, IMAP from the recipient's server to the recipient. A mix of these is the norm.

02 · DNS — Domain Name System

How the Internet finds out where things are

Humans remember names. Computers route packets by numbers. DNS is the enormous, distributed translation machine that bridges the two worlds — and it must do it billions of times each day, without breaking down.

Every time you type www.ntnu.no in your browser, something happens almost instantaneously that is so fast you never notice it: a name must be translated to an IP address before anything else can happen. This translation is seemingly trivial — just look it up in a table — but it must work for every single name on the entire Internet, and every single name must be changeable when someone moves a service to a new server. This is not trivial.

Why not just one big table?

Let us start with the naive solution, which is pedagogically valuable precisely because it does not work. What if we had one central server somewhere in the world, with a gigantic table of all name-to-IP mappings? The client asks, the server answers, done.

The problem with centralization
Comcast's DNS servers alone handle roughly 600 billion queries per day. A central server would (1) be a single point of failure — the entire Internet goes down if it fails, (2) face impossible traffic volumes, (3) be far from most users, and (4) be a nightmare to maintain. It simply does not scale.

The solution — and this is perhaps the most elegant design idea in the entire protocol world — is to make DNS distributed and hierarchical. No single server knows everything. Instead, each server knows a little, and knows whom to ask about the rest.

The hierarchy

Consider the name www.amazon.com. The hierarchy is built from right to left. At the very top sit the root servers. They know nothing about Amazon, but they know who manages .com. Below root sit the TLD servers (Top-Level Domain) — one group for .com, one for .org, one for .no, and so on. The .com server does not know the IP address of www.amazon.com, but it knows which server is authoritative for amazon.com. The authoritative server — operated by Amazon itself — finally knows the actual answer.

There are approximately 13 logical root "servers" in the world, but each is replicated hundreds of times using a technique called anycast — over 1,000 physical machines in total. ICANN (Internet Corporation for Assigned Names and Numbers) administers the root zone. These are the contact point of last resort: a local name server contacts the root servers only when it has not found the answer elsewhere.

Local name servers — the unsung hero

Between you and the entire hierarchy sits something that is not technically part of the DNS hierarchy itself, but is nonetheless the single most important server for your performance: your local name server. Every ISP runs one. NTNU has one. Your company has one. When your machine needs to look up a name, the query always goes here first.

The local server has a local cache of names it has recently looked up. If the answer is in the cache, you skip the entire trip up the hierarchy — you get the answer back in milliseconds. This is why DNS feels instantaneous even though it can actually involve multiple intermediaries. Most queries stop at the cache.

Two ways to query: iterative vs recursive

When a name server needs to go further up the hierarchy, there are two fundamental strategies. Let us follow an example: a host at engineering.nyu.edu wants to know the IP address of gaia.cs.umass.edu.

What you saw in the animation above is an iterative lookup: each server does not respond with a final answer, but with "I don't know, but ask this one instead." The local server does all the work itself — it hops from root to TLD to authoritative.

The other strategy is recursive: the local server asks the root server and says "figure this out for me," and the root server itself takes responsibility for asking the TLD, which asks the authoritative, and the answer bubbles back through the entire chain. This is simpler to implement on the client side, but places a much heavier load on the top layers of the hierarchy — and therefore is typically only used on the last leg, between you and your local server.

DNS records (Resource Records)

What is actually stored in all these name servers? The answer is a distributed database of resource records, or RRs. Each record has the format (name, value, type, ttl) — a name, a value, a type, and a "time to live" that indicates how long the answer is valid.

TypeWhat "name" isWhat "value" is
AA hostnameAn IPv4 address
NSA domain (e.g., amazon.com)Hostname of an authoritative name server
CNAMEAn alias nameThe "canonical" (real) name
MXA domainHostname of a mail server for that domain

The A record is the classic: name to IP. NS points to which server is authoritative. CNAME is an alias — so www.ibm.com can actually be a pointer to something like servereast.backup2.ibm.com, and you as a user never need to know. MX is how your SMTP server finds out where to deliver email for a domain; without MX records, email would not work.

DNS also enables load balancing: a busy website can have many servers with different IP addresses, all registered as A records for the same hostname. The authoritative DNS server rotates the order of addresses for each lookup, so that traffic spreads across many servers. CNAME, on the other hand, provides aliasing — the ability to let one hostname point to another — which is useful, but a different mechanism from load balancing.

How do you get a new domain into DNS?

Imagine you are starting a new company, "Network Utopia," and want the domain networkutopia.com. How do you get it into the global DNS database? The answer is a registrar — a commercially authorized organization (accredited by ICANN) that lets you register domain names.

The process is roughly as follows: you go to a registrar (for example GoDaddy or Domeneshop), check that networkutopia.com is available, pay a fee, and provide the names and IP addresses of your authoritative name servers — let us say dns1.networkutopia.com (212.44.9.129) and dns2.networkutopia.com (212.44.9.130). The registrar then inserts two records in the .com TLD servers:

(networkutopia.com, dns1.networkutopia.com, NS)
(dns1.networkutopia.com, 212.44.9.129, A)

Now the .com TLD servers know that queries about networkutopia.com should be forwarded to your authoritative servers. On those servers you yourself enter A records for your web server (www.networkutopia.com → IP address) and MX records for the email server. From that moment the entire chain is complete: root → TLD → authoritative → final answer.

Caching — the secret sauce

What we have not yet said explicitly is how DNS manages to be so fast. The answer is caching, everywhere. When a name server — any name server — learns a mapping, it stores it in memory for future queries. It stores it until the TTL expires. TLD server addresses are typically cached in local servers virtually all the time, so root servers are almost never contacted for ordinary lookups.

The downside is that cached answers can become outdated. If you move a service to a new IP address, the change will not be visible everywhere on the Internet until all relevant TTLs have expired. This is why DNS changes often take hours or days to "propagate" — it is not a bug, it is the TTL doing its job.

What do you think happens if you send email to someone@example.com, but example.com has no MX record in DNS?

Your mail server will first query for the MX record for example.com. If it does not find one, most implementations will fall back to querying for an A record for example.com directly and try to deliver to that IP address. This is a historical fallback from early SMTP. In practice, all domains that receive email should have MX records — without them you are relying on senders implementing the fallback, and some do not.

DNS messages

DNS mostly uses UDP on port 53 — it is a query-response protocol where each query is short enough to fit in a single UDP packet, and the lower overhead compared to TCP provides much better performance for something that happens billions of times per day. Both queries and responses have the same message format: a header with a 16-bit identifier and some flags, followed by sections for questions, answers, authoritative records, and "helpful additional information."

The identifier is important: when a server receives many responses, it must know which question each response belongs to, and that is what this number is used for. The flags field indicates, among other things, whether the message is a query or response, whether recursion is desired, and whether the answer comes from an authoritative source.

DNS security

DNS is critical infrastructure, and that means some will try to attack it. The most common attack types are:

  • DDoS — bombarding root or TLD servers with traffic. Has been attempted many times; has so far never managed to cripple the Internet, partly due to caching and traffic filtering.
  • DNS poisoning — sending fake responses to a name server so that it caches wrong information, directing users to the wrong destination.
  • DNS amplification — sending DNS queries with a spoofed source address, so that the responses (which are much larger than the queries) are sent to the victim. Used as a DDoS weapon.

The defense is called DNSSEC (RFC 4033), which adds digital signatures to DNS responses so that the client can verify that the answer actually comes from an authoritative source. It is not universally deployed yet, but it is the long-term solution.

Check your understanding
Why are root servers rarely actually contacted, even though they are technically at the top of the hierarchy?
Local name servers almost always have TLD server addresses in their cache, so the iterative lookup process can jump straight to the TLD and proceed from there. Root thus becomes a "contact of last resort" — important that it exists, but rarely actually queried.

03 · Socket programming

When you need to write something that talks

All the protocols we have examined — SMTP, HTTP, DNS — are built on top of something lower: the socket API. When you need to write your own network program, this is where you actually meet the transport layer face to face.

A socket is a peculiar word for something so fundamental. Think of it as a door: on one side stands your process, on the other side stands the transport layer in the operating system. You as the programmer control what happens on the inside of the door. The operating system manages everything on the outside — the packets, the routing, retransmission. The socket is the contract between the two of you.

There are two types of sockets, because there are two transport services you can use: UDP for unreliable datagrams, and TCP for reliable, ordered byte streams. The difference between them is large enough that the APIs actually look different — you use different functions to send and receive — and the choice between them is the first and perhaps most important design decision you make when writing a network program.

A small example program

Throughout the rest of this section we will build a very simple application, in both a UDP version and a TCP version, so that the difference becomes clear. The application is deliberately trivial:

Specification
The client reads a line from the keyboard and sends it to the server. The server converts the line to uppercase and sends it back. The client prints the response. That is it. The entire protocol.

UDP — postcards in the mail

The first thing you need to understand about UDP is that there is no connection. There is no handshake before data is sent. Each packet stands on its own. The sender explicitly attaches the destination IP and port number for every single packet, and the receiver extracts the sender's IP and port from each incoming packet. It is like sending postcards — each postcard is its own little event, and there is no conversation.

The consequences are important: packets can be lost, and they can arrive out of order. The operating system will do nothing about it. If your application requires reliability, you must build it yourself. In return, UDP is extremely lightweight — no startup time, no state, no extra round trip before the first byte can be sent.

Let us look at the code. First the client:

# Python UDP client
from socket import *
serverName = 'hostname'
serverPort = 12000

# Create a UDP socket
clientSocket = socket(AF_INET, SOCK_DGRAM)

message = input('Enter a sentence: ')

# We must attach the address and port for each send
clientSocket.sendto(message.encode(),
                    (serverName, serverPort))

# Read the response — we also learn who replied
modifiedMessage, serverAddress = clientSocket.recvfrom(2048)
print(modifiedMessage.decode())

clientSocket.close()

Note SOCK_DGRAM — that is what says "UDP, please." And note sendto: the second argument is a tuple with the server name and port. We must specify it every single time we send, because the socket has no notion of who it "is connected to." Similarly, recvfrom returns both the data and the sender's address — because each datagram can technically come from any sender.

The server looks like this:

# Python UDP server
from socket import *
serverPort = 12000

serverSocket = socket(AF_INET, SOCK_DGRAM)
serverSocket.bind(('', serverPort))   # Listen on port 12000

print("The server is ready.")

while True:
    message, clientAddress = serverSocket.recvfrom(2048)
    modifiedMessage = message.decode().upper()
    serverSocket.sendto(modifiedMessage.encode(),
                        clientAddress)

The server is almost simpler than the client. It creates a socket, binds it to a specific port (12000), and enters an infinite loop. For each datagram that arrives, it reads both the content and the client's address — and uses exactly that address to send the response back. No "connection" is opened or closed. Each iteration of the loop is a complete transaction in itself.

TCP — a conversation from start to finish

TCP is an entirely different world. Before any data can flow, the client must establish a connection to the server — the famous three-way handshake. Once the connection is established, you have something that behaves like a pipe: bytes you send in at one end come out in the same order at the other end, guaranteed, even if underlying packets were lost and had to be retransmitted.

The elegant design feature — and something that can be confusing the first time you encounter it — is that the server actually has two types of sockets. One is a "welcome socket" that sits waiting for clients to connect. When a client connects, the operating system creates an entirely new socket — a "connection socket" — that is dedicated to exactly this client. The welcome socket goes back to waiting for the next client, and the connection socket is used to communicate with the client that just connected.

This is how a server can talk to many clients simultaneously: one welcome socket, many connection sockets — one per active client. The operating system uses the sender-side port number to keep them apart.

The client code:

# Python TCP client
from socket import *
serverName = 'servername'
serverPort = 12000

clientSocket = socket(AF_INET, SOCK_STREAM)
clientSocket.connect((serverName, serverPort))   # 3-way handshake happens here

sentence = input('Enter a sentence: ')

# No need to specify the address — the socket already knows
clientSocket.send(sentence.encode())

modifiedSentence = clientSocket.recv(1024)
print('From the server:', modifiedSentence.decode())

clientSocket.close()

The differences from the UDP version are small but crucial. SOCK_STREAM instead of SOCK_DGRAM. The new line connect() that did not exist in UDP — this is where the actual TCP connection is established. And once that is done, we use send and recv without specifying any address, because the socket knows who it is connected to.

The server code is where the interesting difference really becomes apparent:

# Python TCP server
from socket import *
serverPort = 12000

serverSocket = socket(AF_INET, SOCK_STREAM)
serverSocket.bind(('', serverPort))
serverSocket.listen(1)            # Start listening for connections

print("The server is ready.")

while True:
    # accept() blocks until a client connects,
    # and then returns a COMPLETELY NEW socket for this client
    connectionSocket, addr = serverSocket.accept()

    sentence = connectionSocket.recv(1024).decode()
    capitalizedSentence = sentence.upper()
    connectionSocket.send(capitalizedSentence.encode())

    connectionSocket.close()       # Close THIS connection, not the welcome socket

Look at serverSocket.accept(). That is where the magic happens. The function blocks until a client tries to connect, and when it does, it returns a pair: a new socket (connectionSocket) and the client's address. We talk with the client through this new socket, and when we are done we close only it — the welcome socket lives on, waiting for the next client.

When do you choose which?

The simple answer is: TCP for most things. The nuanced answer requires that you think about your application's actual needs. Do you need every single byte to arrive? Use TCP. Can you tolerate loss, but need low latency and cannot wait for retransmissions? Use UDP. Are you sending something large enough that TCP connection overhead is negligible? TCP. Are you sending small, frequent, independent messages like DNS lookups or video packets where a packet arriving 200 ms late might as well be discarded? UDP.

Check your understanding
Why must a TCP server have two sockets — a "welcome socket" and a "connection socket" — while a UDP server manages with just one?
UDP treats each datagram as an isolated event — the server uses the same socket to receive from all clients. TCP, on the other hand, has a persistent connection per client, and each of them needs its own socket so that the OS can route incoming bytes to the correct conversation. The welcome socket's only job is to "spawn" new connection sockets.
In closing

The recurring themes

Three different protocols, three different problems — but if you read them side by side, you see that the same design choices appear again and again.

The first theme is centralized vs decentralized. SMTP is decentralized: each organization runs its own mail server. DNS is hierarchical, which is a form of decentralization with coordination — no one knows everything, but the structure ensures you can always find the one who does. Centralization is easy to understand and impossible to scale. Decentralization is the opposite: hard to design correctly, but the only path to the scales at which the Internet operates.

The second theme is stateless vs stateful. SMTP maintains state during a connection (it is in the middle of a conversation). DNS is largely stateless — each query is independent. UDP is fundamentally stateless, TCP is fundamentally stateful. Stateless protocols scale more easily because any server can answer any query; stateful protocols are necessary when something must be remembered across requests.

The third theme is "complexity at the edge." This is perhaps the most characteristic feature of Internet architecture as a whole. The network itself — routers, cables, IP — is deliberately dumb. All the interesting intelligence sits in the endpoints: in mail servers, in DNS resolvers, in the programs you yourself write with sockets. This design choice is the reason the Internet could grow without needing to be upgraded centrally, and it is the reason a student with a laptop in Trondheim can invent a completely new application tomorrow and roll it out globally without asking anyone for permission.

The fourth and final theme is reliable vs unreliable message delivery — and the insight that there is no single right choice. TCP and UDP exist side by side because they solve different problems. The same holds true up the stack: SMTP is built on TCP because email must arrive, while DNS is built on UDP because fast lookups that can be retried are better than reliable lookups that are slow.

The most important takeaway
Protocols are not magic. Every single design choice you have seen — push vs pull, hierarchy vs centralization, datagram vs stream — was made because the alternative would not have worked at the scale or with the constraints that existed. When you understand which problem a protocol solves, the form it takes becomes almost inevitable.
