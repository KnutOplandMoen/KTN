01 · Where apps live

Programs at each end of the network

Before we talk about HTTP or BitTorrent, we need to understand one simple thing: where does a network application actually run?

A browser runs on your machine. A web server runs on another. Between them lies the Internet — millions of routers and links that move packets around. The absolutely central idea in the application layer is this: you only write code for the end systems. The routers in the core run no user applications; they merely forward packets. This is the reason a student can invent a completely new network service tonight and roll it out across the globe tomorrow, without having to update anything in the network's infrastructure.

Writing a network application thus means writing two (or more) programs that run on different machines and exchange messages over the network. A web server program talks with a browser program. Two Skype clients talk with each other. A BitTorrent client talks with dozens of other clients simultaneously. The pattern is the same everywhere: processes on end systems sending messages through the network.

Processes, sockets, and addresses

Inside the operating system, a running app is a process. Two processes on the same machine communicate via mechanisms the operating system provides (shared memory, pipes, etc.). Two processes on different machines communicate by sending messages through the network — and the gateway out of the process is called a socket.

The picture you should have in mind: the socket is a door. The sending process pushes a message out through the door and trusts that the transport infrastructure on the other side delivers it to another socket at the receiving process. Two sockets are involved in each communication — one at each end.

For the message to arrive, the receiving process must have an identifier. The host's IP address is not enough — a single machine typically runs dozens of processes simultaneously. The identifier therefore consists of two parts: IP address (which machine) and port number (which process on that machine). An HTTP server typically listens on port 80, a mail server on port 25.

Think of the IP address as the street address of an apartment building, and the port number as the apartment number. Both must be on the envelope for the letter to reach the right person.

What an application protocol actually is

When two programs need to communicate, they must agree on the rules. An application protocol defines four things:

Message types — for example request and response. Message syntax — which fields exist, and how are they delimited? Message semantics — what do the values in the fields mean? Rules — when and how are messages sent, and how does one respond?

Some protocols are open: defined in RFCs, freely available, so that anyone can implement them. HTTP and SMTP are classic examples — it is precisely because they are open that any browser can talk to any web server. Other protocols are proprietary — Skype is an example — and work only within a single vendor's ecosystem.

02 · Two ways to organize it

Client–server, or everyone against everyone

When two machines need to cooperate, who takes the initiative? Who is always on? The answer divides the entire application world in two.

The classic model is client–server. A server machine is always on, has a fixed IP address, and waits for clients to connect. The clients — your browser, your email app, your FTP client — connect when they have a need, send a request, receive a response, and disconnect again. Clients never talk directly to each other; all traffic goes through the server. Examples: HTTP, IMAP, FTP. The model is easy to reason about, and because the server has one known address, there is no doubt about whom to contact.

The obvious downside is that the server quickly becomes a bottleneck. If you need to distribute a large file to a million clients simultaneously, one machine must upload that file a million times. That scales poorly — and we will soon examine this mathematically.

The alternative model is peer-to-peer. Here there is no always-on server. Arbitrary end systems — peers — talk directly with each other. A peer requests a service from another peer, and itself provides services back to others. The fascinating property is self-scaling: each new peer that enters the system brings not only new demands, but also new capacity. The more people who want the file, the more people there are who can share it further.

The price you pay is complexity. Peers are only intermittently connected, their IP addresses change, and there is no central directory. Classic examples are BitTorrent (file sharing), KanKan (streaming), and Skype (VoIP).

The hybrid reality

In practice, nearly all modern systems are hybrids. Skype uses peer-to-peer for the actual conversation, but needs centralized servers to find out where the other party is. BitTorrent uses P2P for the file transfer, but often a centralized "tracker" or distributed hash table to discover other peers. The pure form is rare; what matters is understanding both models because systems borrow features from both.

03 · What does the app need from the layer below?

The order to the transport layer

An app is picky. It wants certain things from the transport layer — but not all apps want the same things.

When you design an application protocol, you must choose which transport service to sit on top of. There are two main options on the Internet — TCP and UDP — and they give you very different guarantees. To choose wisely, you need to know what your app actually requires.

There are four dimensions at play. Data reliability: can the app tolerate some lost packets? File transfer requires 100% reliability — a single lost byte and the entire file is corrupt. Audio and video, on the other hand, can tolerate some loss; a glitch here and there produces a bit of static, not catastrophe. Timing requirements: must data arrive within a certain time? Internet telephony and games need low delay to feel usable. A file download does not care about a second more or less. Throughput: does the app need a minimum rate? Streaming video does. Email does not. Security: should data be encrypted, integrity-checked, authenticated?

TCP vs. UDP, in brief

TCP gives you reliable transfer (all bytes arrive, in correct order), flow control (the sender does not overwhelm a slow receiver) and congestion control (the sender slows down when the network is congested). In addition, TCP is connection-oriented — a connection must be set up between the parties before data can flow. TCP does not provide timing guarantees or minimum throughput, and it does not provide security by itself.

UDP is the opposite: no reliability, no flow control, no congestion control, no connection setup. You send a packet; it may or may not arrive. Why does UDP exist then? Because it is simple and fast, and because some apps prefer to handle reliability themselves — or actually do not want it. Real-time voice calls would rather lose some packets than wait for retransmissions.

Securing TCP with TLS

Plain TCP and UDP sockets are unencrypted. If you send a password through a plain TCP socket, it travels in clear text across the Internet — and anyone along the way can read it. The solution is called Transport Layer Security (TLS), which sits as a layer on top of TCP and provides encryption, data integrity, and endpoint authentication. TLS is implemented as libraries in the application layer — apps call TLS functions, which in turn communicate with TCP. Plaintext sent into a TLS socket comes out again at the other end, but over the network it has traveled encrypted.

04 · The Web and HTTP

The protocol that builds a web page

When you type a URL in the browser, what actually happens? The answer is HTTP — the Web's application protocol, and perhaps the most widely used protocol in the world.

A web page is rarely one thing. It is an HTML file that references other objects — images, stylesheets, scripts, fonts, videos — and each of these objects may be fetched from different servers on the Internet. When the browser is to display a page, it must first fetch the HTML, then parse it to discover which other objects are needed, and then fetch all of those as well. This is a choreographed ballet of requests and responses, and it is HTTP that conducts it all.

HTTP stands for HyperText Transfer Protocol. It follows a client–server model: the browser is the client that sends requests, the web server is the server that responds. HTTP uses TCP under the hood — because we need reliable transfer so that the HTML does not arrive corrupted. The client initiates a TCP connection to the server on port 80 (or 443 for HTTPS), the server accepts, HTTP messages are exchanged, and finally the connection is closed.

A critical property: HTTP is stateless. The server remembers nothing about previous requests from the same client. Each request is a blank slate. That sounds like a weakness — and we shall see that it creates challenges that must be solved with cookies — but it is also an enormous strength. Stateless protocols are simple to implement, simple to scale, and if a server crashes, a new one can take over without needing to reconstruct any "session state."

Two flavors of HTTP connections

In early HTTP days (HTTP/1.0), non-persistent connections were used: one TCP connection per object. You open the connection, fetch the HTML, close. Open a new connection, fetch the first image, close. Open a new connection, fetch the second image, close. For a page with ten images, that means eleven TCP setups. Each setup costs one RTT just to get started, plus OS overhead.

HTTP/1.1 introduced persistent connections: open one TCP connection, send many requests over it, close when you are done. The difference may seem small, but it is significant — especially over connections with high RTT.

05 · The HTTP message, unfolded

What a request and a response actually contain

HTTP messages are remarkably readable. You can practically talk to a web server from a keyboard via Telnet.

There are two types of HTTP messages: requests (sent from client to server) and responses (server to client). Both are plain ASCII — no binary obscurity — and consist of three parts: a start line, a number of header lines, and an optional body.

Request
GET /index.html HTTP/1.1
Host: www.cs.umass.edu
User-Agent: Firefox/3.6
Accept: text/html
Accept-Language: en-us,en
Accept-Encoding: gzip,deflate
Connection: keep-alive

(blank line marks the end)
Response
HTTP/1.1 200 OK
Date: Sun, 26 Sep 2010 20:09:20 GMT
Server: Apache/2.0.52
Last-Modified: Tue, 30 Oct 2007
Content-Length: 2652
Content-Type: text/html

<html>...</html>

The request's first line — called the request line — has the form METHOD URL VERSION. The header lines follow as name: value. A blank line (CRLF) marks the end of the header. After the header, a body may follow, for example data from a filled-in form.

The methods

HTTP defines several methods, each with a clear role. GET requests an object; any parameters are placed in the URL after a question mark. POST sends data to the server — typically from a web form — in the request body. HEAD requests the header of an object without the content itself; useful for debugging and for caches that want to check if something has changed. PUT uploads a new file to a specified URL and replaces any existing content there.

Status codes

The response's first line contains a three-digit status code. You probably know some of them already:

200 OKThe request succeeded; the object is included in the response.
301 Moved PermanentlyThe object has been moved; the new address is given in the Location header.
400 Bad RequestThe server did not understand the request.
404 Not FoundThe requested document does not exist on the server.
505 HTTP Version Not SupportedThe server does not support the HTTP version the client used.

Try it yourself

You can talk directly to a web server from the terminal. Type telnet gaia.cs.umass.edu 80, and you have a TCP connection on port 80. Type a GET request manually (end with two enters), and watch raw HTTP response come back. It is one of the fastest ways to demystify how the web actually works.

06 · State in a stateless world

Cookies, or why your browser knows who you are

HTTP is stateless — but the shopping cart in the online store knows what you put in it. How does that work?

The statelessness of HTTP is a blessing for scalability and simplicity, but a curse if you actually want to build an application where the user should be able to log in, fill a shopping cart, or pick up where they left off yesterday. How can a server recognize the same user across independent requests? The answer is one of the Web's most important inventions: cookies.

The idea is simple. The first time a user visits a website, the server sends a unique identifier back in a special header field — Set-Cookie: 1678. The browser stores this in a cookie file, associated with the domain. Next time the user requests something from the same website, the browser automatically includes the cookie in the request — Cookie: 1678. Now the server can look up the identifier in its own database and determine: "Ah, that is the user who put two books in the shopping cart ten minutes ago."

There are four moving parts in the system: a Set-Cookie header in an HTTP response, a Cookie header in subsequent HTTP requests, a cookie file on the user's machine (managed by the browser), and a database on the server side where the cookie is linked to actual information.

Cookies are used for many useful things: authorization (who are you logged in as?), shopping carts, recommendations, session state for webmail. But they are also one of the main mechanisms behind tracking on the web. Third-party persistent cookies — cookies set by domains other than the one you see in the address bar — allow the same identifier to follow you across many different websites, building a very detailed profile of your activity.

Norwegian regulations from 2025

The Norwegian Parliament passed a new Electronic Communications Act that took effect on January 1, 2025. It requires that consent to cookies meets GDPR requirements: voluntary, specific, informed, unambiguous, given through an active action, documentable, and possible to withdraw as easily as it was given. This is the reason nearly all websites now show you a cookie banner on first visit.

HTTP is stateless, but cookies provide state. Why didn't they simply make HTTP stateful from the start, instead of adding cookies later?

Statelessness is a deliberate design decision that provides great advantages: servers do not need to remember anything between requests, which makes it easy to scale (add more servers behind a load balancer — any of them can answer any request). If the server crashes, it does not need to reconstruct any session state. Stateless protocols are also simpler to implement and simpler to debug. Cookies let you add state where you need it, without imposing it on the entire protocol. It is an "opt-in" system: only those applications that actually need state pay the cost.

07 · Web cache and conditional GET

Don't fetch what you already have

The fastest request is the one you never send.

A web cache — or proxy server — is an intermediary that remembers previous responses. The user's browser is configured to send all HTTP requests through the cache instead of directly to the origin server. When a request arrives, the cache first checks whether it already has the object. If yes, it delivers it immediately. If no, it fetches the object from the origin server, stores a copy, and delivers it onward to the client.

The cache thus acts simultaneously as a server (toward the client) and as a client (toward the origin server). This provides two important benefits: shorter response time for the user, because the cache is typically closer than the origin server, and less traffic on the institution's access link, because popular content only needs to be downloaded once. For a university ISP or an office network, this can save enormous amounts of bandwidth.

The problem: how does the cache know it has a valid copy?

What if the content on the origin server has changed since the cache stored its copy? Then the cache serves stale content to the user — embarrassing. The solution is conditional GET. The cache sends a regular GET request, but adds a header field: If-Modified-Since: <date>.

The server checks whether the object has been modified after that date. If not, it responds with 304 Not Modified — a small message with no content at all. The cache then knows its version is still valid and can safely deliver it. If the object has been modified, the server responds with 200 OK and the new content, just like a regular GET. This is an elegant optimization: in the common case — where the content has not changed — the object does not need to be transferred at all, only the small 304 message.

08 · HTTP/2 and head-of-line blocking

When one large file blocks everything else

HTTP/1.1 was good, but it had one annoying problem that HTTP/2 was created to fix.

HTTP/1.1 let you pipeline requests over one TCP connection, but the server responded in the same order as the requests arrived (FCFS — first-come-first-served). Imagine a web page containing one large video and three small images. The client requests all four in order: O₁ (the video), O₂, O₃, O₄. The server begins sending O₁, and because it is large, the three small images must wait behind in the queue. This is called head-of-line blocking — the object at the front blocks everything behind it.

The result is that the user sees a blank page while the video is being transferred, even though the three small images could have been transferred in an instant. The browser's main trick to work around this in HTTP/1.1 was to open multiple parallel TCP connections to the same server, so that small objects could be fetched in parallel with the large one. It works, but it is cumbersome and weakens congestion control.

HTTP/2 (RFC 7540, 2015) solves this by breaking objects into smaller frames and interleaving frames from different objects on the same connection. The server can also prioritize frames based on what the client has requested — not necessarily FCFS. Three small objects then get their frames transmitted between frames from the large object, arriving quickly while the large one is still being transferred.

HTTP/2 also introduced server push: the server can send objects to the client before the client has requested them. When the server receives a request for an HTML page, it knows the client will soon need the CSS file and some images — and can proactively push these out instead of waiting for the client to parse the HTML and send new requests. This eliminates one extra RTT for each object that is pushed.

HTTP/2 still has a remaining problem, however: it still sits on top of one TCP connection, and if a TCP packet is lost, all objects must wait for the retransmission. HTTP/3 solves this by replacing TCP with a new transport protocol called QUIC, built on UDP. QUIC gives each stream its own independent error handling, so that a packet loss in one stream does not block the others. More on this in the chapter on the transport layer.
