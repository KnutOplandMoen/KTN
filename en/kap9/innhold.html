Multimedia Networking

How audio and video travel over a network that really only promises "best effort" — and what happens when the packets don't arrive on time.

01 · Fundamentals

Audio and video as bits

Before we can send multimedia over a network, we must understand how analog signals become a stream of bits.

Sound is pressure waves in the air. Video is a sequence of images displayed fast enough for the eye to perceive motion. Neither is naturally "digital" — they are continuous, analog quantities. To send them over a packet network, we must first convert them into a stream of bits, and that is where sampling and quantization come in.

Audio: sampling and quantization

An analog audio signal is sampled at a fixed rate — the value of the signal is measured at regular intervals. Each measurement is quantized, meaning rounded to the nearest permitted value. If we use 8 bits per sample, we have 28 = 256 possible values. The result is a stream of numbers representing the sound.

Video: spatial and temporal coding

A video is a sequence of images (typically 24–30 frames per second), where each image is a grid of pixels. Raw video requires enormous bandwidth, but there are two types of redundancy we can exploit for compression:

Spatial coding

Within a single frame, there are large areas of the same color. Instead of sending N identical pixels, we send just the color and the count — "200 purple pixels". This is the idea behind all image compression.

Temporal coding

Between two consecutive frames, the difference is often minimal — perhaps just a small movement in one corner. Instead of sending the entire next frame, we send only the difference from the previous frame. This is why MPEG video is so much more efficient than sending each frame individually.

CBR vs. VBR

When encoding video, we can choose between two strategies:

  • CBR (Constant Bit Rate): The video is encoded at a fixed bit rate throughout. Simple for the network to plan for, but may give unnecessarily low quality in quiet scenes or too poor quality in complex scenes.
  • VBR (Variable Bit Rate): The bit rate varies according to how complex the content is. A simple scene with little movement uses few bits, while an action scene uses many. Better quality, but harder for the network to handle.

02 · Application types

Three types of multimedia applications

Not all multimedia has the same requirements from the network.

Multimedia over networks can be divided into three categories with widely different network requirements. It is important to distinguish them, because the solutions we need are different for each.

1. Streaming stored content

  • Video/audio is pre-recorded and stored on a server
  • The client can begin playback before the entire file is downloaded
  • The server can send faster than the playback rate — the client buffers
  • Examples: YouTube, Netflix, Spotify

2. Conversation (voice/video)

  • Interactive communication between people
  • Very strict requirements on delay — over 400 ms ruins the conversation
  • Tolerates some packet loss, but not much delay
  • Examples: Skype, Zoom, Teams, VoIP telephony
3. Live streaming

A middle ground: content is streamed in real time (football match, concert), but is not interactive. A few seconds of delay can be tolerated (that is why you sometimes hear your neighbor cheer before you see the goal). The requirements are roughly the same as for stored streaming, but you cannot fast-forward.

The common thread is that all three types are time-sensitive — bits that arrive too late are worthless. An email that takes 2 extra seconds does not matter, but 2 extra seconds of delay in a phone call makes it unusable. The rest of this chapter is about handling this time sensitivity over a network that only promises "best effort".

03 · Stored video

Streaming stored video

The client plays one end while the server is still sending the other — and the buffer in the middle makes it all possible.

The main challenge with streaming is simple to explain: the video was recorded at a fixed rate (e.g., 30 frames per second), and it must be played back at exactly the same rate to look correct. But the network delivers packets with variable delay — sometimes a bit faster, sometimes a bit slower. This variability is called jitter, and it is what the client must compensate for.

Continuous playout constraint

Once playback has begun, it must continue at a steady rate. If packets needed for the next frame have not arrived yet, the video freezes — the classic "buffering" animation we all hate. We cannot send the packets back in time, so the only strategy is to delay the start of playback, so we build up a buffer first.

Client-side buffering

The idea is elegant: the client has a buffer with room for a certain amount of video. The server fills the buffer at variable rate x(t) (affected by network conditions), while the client drains the buffer at constant playback rate r.

The trade-off: playout delay

The longer we wait before starting playback, the more buffer we build up — and the safer we are against short periods where the network is slow. But the user does not want to wait. This trade-off is fundamental:

04 · Transport choice

UDP vs. HTTP streaming

Two entirely different strategies for getting video bits from server to client.

Historically, there have been two main approaches to streaming video. In the early days, UDP was most commonly used; today, HTTP/TCP has won almost completely. It is worth understanding both and why the pendulum swung.

Streaming over UDP

  • Server sends at a rate suitable for the client, often equal to the encoding rate (CBR)
  • The sender does not care about congestion in the network — can "flood" a bottleneck
  • Short playout delay (2–5 sec) to remove jitter
  • Error correction at the application layer if there is time
  • Uses RTP for multimedia payload
  • Often blocked by firewalls (UDP traffic is filtered)

Streaming over HTTP/TCP

  • Video file is fetched with a standard HTTP GET
  • TCP provides reliable, ordered delivery (retransmission)
  • Send rate varies due to TCP's congestion control
  • Larger playout buffer needed to smooth out the variation
  • Passes firewalls without issue (port 80/443)
  • Used by YouTube, Netflix, and virtually everything today

The reason HTTP/TCP won is pragmatic: it passes firewalls, it requires no special server infrastructure (a regular web server suffices), and TCP provides reliable delivery so you do not have to handle loss yourself. The trade-off is higher playout delay, but for streaming stored video that is acceptable.

05 · VoIP

Voice-over-IP: conversation over packet networks

The requirements for interactive speech are fundamentally different from stored video — delay is the enemy.

When two people talk together, they expect a response within a fraction of a second. Our brains are incredibly sensitive to delays in conversations — already at 150 milliseconds we notice something is "off", and at 400 ms the conversation breaks down into an awkward dance of "were you talking? no, you first". This delay sensitivity makes VoIP a much harder problem than streaming video.

VoIP characteristics

A typical VoIP stream looks like this:

  • The speaker alternates between talk spurts and silence. Packets are generated only during talk spurts.
  • During talking: 64 kbps (= 8 Kbytes/s) with PCM encoding.
  • The audio is split into 20 ms chunks — each chunk is 160 bytes of audio data.
  • An application header is added to each chunk, and the result is packed into a UDP or TCP segment.
  • The application sends one packet every 20 milliseconds during a talk spurt.

Delay requirements

End-to-end delay

< 150 ms: good — the conversation feels natural.
150–400 ms: noticeable delay, but usable.
> 400 ms: unacceptable — the conversation becomes impossible.
The delay includes everything: packetization, network delay, playout delay at the receiver.

Packet loss and delay loss

VoIP must handle two types of loss:

Network loss

  • IP datagrams are lost due to congestion in the network (router buffer overflow)
  • The usual form of loss we know from the TCP world

Delay loss

  • The packet does arrive, but too late to be played out
  • Effectively the same as loss — the chunk is useless
  • Typical maximum tolerated delay: 400 ms

An important point: VoIP tolerates some loss. Depending on audio encoding and techniques for loss concealment, one can tolerate 1–20% packet loss without the conversation becoming unintelligible. That is a dramatic difference from e.g., file transfer, where every lost byte is catastrophic.

06 · Jitter

Jitter and playout delay

Constant send rate into the network, variable delay through it — and a buffer that straightens it out again.

The VoIP sender sends packets at regular intervals (every 20 ms during a talk spurt). But the network delivers them with variable delay — just as with video streaming. This variation in delay is jitter, and it must be compensated by the receiver. The solution is, again, a buffer — but now the trade-off is about milliseconds, not seconds.

Fixed playout delay

The simplest strategy: the receiver decides on a fixed delay q, and plays out each audio chunk exactly q milliseconds after it was generated by the sender.

  • If an audio chunk has timestamp t, it is played out at time t + q.
  • If the chunk arrives after t + q → it is lost (too late).
  • Large q: fewer packets "too late" → lower loss, but longer delay in the conversation.
  • Small q: better interactivity, but more packets do not make it in time.

Adaptive playout delay

Instead of choosing a fixed q, we can make it adaptive: we estimate the network delay continuously and adjust the playout delay at the start of each new talk spurt. Silent periods are slightly compressed or extended to absorb the change — the listener does not notice this.

The estimation uses an EWMA (Exponentially Weighted Moving Average), exactly the same idea TCP uses to estimate RTT:

di = (1 − α) · di-1 + α · (ri − ti)

Here di is the estimated network delay after the i-th packet, α is a small constant (typically 0.1), ri is the time the packet was received, and ti is the timestamp (when it was sent). The expression (ri − ti) is the actual measured delay for packet i.

But average delay alone is not enough — we also need a measure of the variation. We estimate the deviation the same way:

vi = (1 − β) · vi-1 + β · |ri − ti − di|

The playout time for the first packet j in a new talk spurt is then set to:

playoutj = tj + dj + K · vj

Here K is a constant (typically 4). Note the parallel to TCP: there, the timeout is set to EstimatedRTT + 4 · DevRTT — exactly the same structure. The average captures the "normal state", and K · v adds a safety margin proportional to how much the delay varies. All subsequent packets in the same talk spurt are played out at fixed 20 ms intervals from this starting point.

Detecting start of a new talk spurt

The receiver must know when a new talk spurt starts, because that is when the playout delay can be adjusted. Without packet loss, it is simple: if the difference between two consecutive timestamps is > 20 ms, there has been a silence period. With possible packet loss, the receiver looks at both timestamps and sequence numbers — if the timestamp gap is > 20 ms and no sequence numbers are missing, it is a new talk spurt.

07 · Loss recovery

FEC and interleaving

Three techniques for recovering lost audio without waiting for retransmission.

In VoIP, we do not have time for the usual TCP method of requesting retransmission — a retransmission takes at least one RTT, and that can easily exceed our delay budget. We need techniques that allow the receiver to recover lost packets without help from the sender.

1. Simple FEC (XOR)

For each group of n audio chunks, the sender creates one extra redundant chunk by XOR-ing all n originals together. The sender thus sends n+1 packets instead of n, increasing bandwidth by a factor of 1/n.

Example

With n = 4 we send 5 packets per group. If one of the 5 packets is lost, the receiver can reconstruct it from the other 4 (XOR is reversible). If two or more are lost, this method does not provide enough information. The cost: 25% extra bandwidth and increased playout delay (we must wait for the entire group).

2. Piggyback with low-quality stream

A more elegant variant: the sender attaches a low-resolution copy of a previous audio chunk in each packet. For example, the nominal stream may use PCM at 64 kbps, while the redundant stream uses GSM at 13 kbps.

If packet 3 is lost, we lose chunk 3 in full quality, but chunk 2 can be recovered from the low copy in packet 4. The result is that only consecutive losses produce audible gaps. The overhead is modest (13 kbps extra in this example).

3. Interleaving

A third technique that requires no extra bandwidth at all. The idea: each 20 ms audio chunk is split into four 5 ms units. Units from different chunks are mixed together in the packets. If one packet is lost, we lose only one small 5 ms unit from four different chunks — instead of one entire contiguous 20 ms chunk. Each gap is so short it is almost inaudible.

Trade-off

Interleaving provides no redundancy overhead, but requires the receiver to wait for enough packets to reassemble the original chunks. That means increased playout delay — it always costs something.

08 · Skype

Skype: P2P VoIP in practice

An early example of large-scale VoIP — with supernodes, overlay networks, and NAT traversal.

Skype was for many years the dominant example of VoIP over the Internet. It used a proprietary, encrypted protocol that was reverse-engineered by researchers. The architecture is interesting because it combines P2P elements with centralized control.

Architecture

  • Skype clients (SC): ordinary users running the Skype application. During a call, two clients connect directly to each other for the actual VoIP data stream.
  • Supernodes (SN): selected Skype peers with special functions — they help locate other users and route traffic through an overlay network.
  • Overlay network: the supernodes form an overlay network among themselves to find users' IP addresses.
  • Login server: a centralized server for authentication (username/password).

Setting up a call

  1. The client connects to a supernode (the IP address is cached locally) via TCP.
  2. Logs in to the centralized login server.
  3. Gets the IP address of the person to call from the supernodes' overlay (or from the contact list).
  4. Initiates the call directly to the other client.

The NAT problem and the relay solution

The interesting problem arises when both call participants are behind NAT. A NAT does not let outsiders initiate a connection to a device on the inside — that is the whole point of NAT. So how do two "locked-in" clients connect to each other?

The solution: Alice and Bob both maintain an open TCP connection to their respective supernode (the connection is initiated from inside the NAT, so it is permitted). When Alice wants to call Bob, she signals through her SN to Bob's SN, which uses its open connection to Bob. The actual voice data can then be relayed through the supernodes. It is not optimal (twice as many hops), but it works even when both parties are behind NAT.

09 · RTP

RTP — Real-Time Protocol

A thin protocol that gives multimedia packets what they need: type identification, sequence numbers, and timestamps.

RTP (RFC 3550) is the protocol that gives structure to multimedia packets. It is not a transport protocol in the traditional sense — it runs on top of UDP and provides a set of fields that applications need to handle real-time data, but that UDP does not offer: information about what kind of data the packet contains, in what order it belongs, and exactly when it was generated.

What RTP gives us

RTP transports, but does not guarantee

RTP provides payload type identification, sequence numbering, and timestamping. But it provides no guarantee of timely delivery, no guarantee against loss, and no guarantee of ordering. It is just a framework that the application can use to do its best — for example, adaptive playout delay based on the timestamps.

RTP on top of UDP

RTP libraries offer a transport interface that extends UDP with the fields multimedia needs. An RTP packet consists of an RTP header followed by audio data (payload), and the entire packet is encapsulated in a UDP segment. From the network's perspective, it is just a regular UDP packet — routers along the way never see the RTP header and treat the packet with ordinary best-effort.

Example: 64 kbps PCM over RTP

A VoIP application sending 64 kbps PCM-encoded speech over RTP does the following:

  1. Collects 160 bytes of audio data every 20 milliseconds (= 8,000 bytes/s = 64 kbps).
  2. Adds an RTP header with payload type, sequence number, and timestamp.
  3. Packs everything into a UDP segment and sends it.
  4. The sender can change the encoding type mid-call — the RTP header tells the receiver about the change via the payload type field.

The RTP header in detail

FieldSizeFunction
Payload type 7 bits Identifies which encoding is used. The sender can change encoding mid-stream (e.g., from PCM to GSM), and the receiver sees the change here.
Sequence number 16 bits Increments by 1 for each sent RTP packet. Lets the receiver detect packet loss and put packets in the correct order.
Timestamp 32 bits The sampling instant of the first byte in the packet. For 8 kHz audio, the timestamp increments by 1 per sample (125 μs), i.e., by 160 per 20 ms packet. The clock keeps ticking even during silence periods.

RTP and QoS

One final important point: RTP provides no QoS guarantees. RTP packets are encapsulated in ordinary UDP segments, and routers in the network see only an IP datagram with a UDP header. They make no special effort to deliver RTP packets faster or more reliably than other packets. All intelligence — adaptive playout, FEC, jitter buffer — resides in the endpoints, not in the network.

Interoperability

One of the great advantages of RTP is that two VoIP applications from different vendors can communicate, as long as both use RTP. The payload type field and the standardized encodings ensure that the receiver knows how to decode the data, regardless of which application sent it.
