00 · Transport layer services

What the transport layer actually does

The network layer delivers packets between machines. The transport layer lifts communication one level up — to processes.

Imagine a house where twelve children live. Another house, on the other side of town, also houses twelve children. Every day the children send letters to each other. The postal system delivers envelopes to the right house — but it is Ann and Bill, one child in each house, who receive the mail and distribute it to the right sibling. The postal system is the network layer: it delivers to the house address. Ann and Bill are the transport layer: they deliver to the right person inside the house.

This analogy captures the absolutely central distinction:

LayerCommunication
Network layerLogical communication between hosts — IP addresses identify machines.
Transport layerLogical communication between processes — port numbers identify applications.

The transport layer builds upon the network layer, but it cannot perform miracles. The network layer (IP) offers a best-effort service without any guarantees. The transport layer can add reliability and ordering (TCP), but it cannot force the network to provide better bandwidth or lower latency.

Sender and receiver actions

The transport layer performs concrete actions on both sides:

Sender

Receives an application message from the layer above. Determines header values (port numbers, etc.), creates a segment, and delivers the segment down to IP.

Receiver

Receives a segment from IP. Checks the header values. Extracts the application data. Demultiplexes the message up to the correct socket (and thus the correct process).

Two transport protocols

The Internet gives applications two choices:

ProtocolProperties
TCPReliable, ordered delivery. Flow control, congestion control, connection establishment. Costs time and resources.
UDPUnreliable, unordered delivery. No handshake, no state information, minimal overhead. Fast and simple.
What the transport layer cannot provide Neither TCP nor UDP can guarantee latency or bandwidth. These properties require support in the network core, and IP provides no such guarantees.
Check your understanding

What is the fundamental difference between the network layer and the transport layer?

Correct. The network layer (IP) delivers packets to the right machine. The transport layer uses port numbers to deliver onward to the right process on that machine.
01 · Multiplexing and demultiplexing

The right packet to the right process

The core task of the transport layer: gather data from many sockets on the sender side, and deliver them to the correct socket on the receiver side.

Multiplexing and demultiplexing are two sides of the same coin. Multiplexing happens at the sender: the transport layer gathers data from different application sockets, adds transport headers (including port numbers), and sends the segments downward. Demultiplexing happens at the receiver: the transport layer examines header information in incoming segments and delivers the data up to the correct socket.

How demultiplexing works

When a host receives an IP datagram, it contains:

  • Source IP address Who sent the datagram.
  • Destination IP Who should receive it.
  • Source port number From the segment header — 16 bits.
  • Dest. port number From the segment header — 16 bits.

The host uses IP addresses and port numbers to direct the segment to the correct socket. But how this happens differs between UDP and TCP.

Connectionless demultiplexing (UDP)

A UDP socket is identified by only two things: destination IP and destination port. The consequence is simple but important:

Key insight

If two UDP datagrams have different source IP and/or source port, but the same destination IP and port, they end up in the same socket at the receiver. UDP only cares about where the packet is going, not where it comes from.

Connection-oriented demultiplexing (TCP)

TCP does it differently. A TCP socket is identified by a 4-tuple:

  • source IP
  • source port
  • destination IP
  • destination port

The consequence: even if three segments arrive at the same server with the same destination IP and port (e.g., port 80), they will be delivered to different sockets if they have different source IP or source port. A web server can thus have hundreds of simultaneous TCP connections — all on port 80 — and keep them separate because each connection has a unique 4-tuple.

Check your understanding

Two UDP datagrams arrive at a server. They have different source IPs but the same destination IP and port. What happens?

Correct. UDP identifies a socket using only the destination IP and port. Source information is not used for demultiplexing, so both end up in the same socket.
02 · UDP

Connectionless transport: UDP

UDP does almost nothing — and that is precisely the point. Minimal overhead, maximum freedom.

User Datagram Protocol is the simplest transport protocol on the Internet. It does almost nothing beyond what IP already provides. No connection establishment, no state, no delivery guarantee, no ordering guarantee, no flow control, no congestion control. Each UDP segment is handled independently of all others.

Why choose something so primitive? Because the absence of guarantees has concrete advantages:

PropertyAdvantage
No handshakeNo extra RTT to set up a connection — data can be sent immediately.
No stateSender and receiver hold no connection information. Servers can handle many more clients.
Small headerOnly 8 bytes of overhead vs. 20+ bytes for TCP.
No congestion controlThe application can send as fast as it wants — useful for real-time applications that tolerate some loss.

Who uses UDP?

UDP is surprisingly widespread:

  • DNS — fast lookups without setting up a connection
  • SNMP — network monitoring where simplicity matters
  • Streaming — loss-tolerant, latency-sensitive (though services like Netflix often use TCP)
  • HTTP/3 — builds reliability and congestion control on top of UDP via QUIC
Reliability on top of UDP If an application needs reliable delivery but uses UDP (e.g., HTTP/3), it must implement reliability and congestion control itself at the application layer.

Anatomy of a UDP segment

The UDP header is minimalist — only 8 bytes:

FieldPurpose
Source PortThe sender's port number. The receiver can use this to send a reply back.
Dest PortThe port number the segment should be delivered to at the receiver.
LengthThe length of the entire UDP segment (header + data) in bytes.
ChecksumUsed to detect bit errors in the header or data.

Sender and receiver actions

UDP sender

Receives an application message. Sets source and destination port. Computes the length and checksum. Packs everything into a segment and delivers it to IP.

UDP receiver

Receives a segment from IP. Checks the checksum. Extracts the application data. Demultiplexes the message up to the correct socket based on the destination port.

03 · The UDP checksum

Error detection with one's complement

The checksum is UDP's only line of defense. It is simple, cheap, and far from perfect.

The idea behind the checksum is straightforward: the sender sums all 16-bit words in the segment (header + data + parts of the IP header), takes the one's complement of the sum, and places the result in the checksum field. The receiver performs the same computation. If the answer does not match, she knows that something was altered in transit.

Step by step

Computation

1. Treat the contents as a sequence of 16-bit integers.
2. Sum them using one's complement addition (where a carry out of bit 15 is added back to bit 0 — wraparound).
3. Take the one's complement of the sum (invert all bits). This is the checksum.

An example

Suppose we add two 16-bit numbers:

Computation

1110 0110 0110 0110
1101 0101 0101 0101
────────────────────
1 1011 1011 1011 1011 ← wraparound carry
  1011 1011 1011 1100 ← sum (after wraparound)
  0100 0100 0100 0011 ← checksum (one's complement)

Weak, but better than nothing

The checksum catches many common errors — such as a single bit flip. But it is weak: if two bits flip in just the right way, they can "cancel out" each other without changing the sum. The checksum provides no guarantee that the data is unaltered — it only gives a reasonable chance of detecting errors.

Why one's complement? One's complement addition has a useful property: it is order-independent. You can sum the words in any order and get the same result. This simplifies the implementation.
Check your understanding

What is a weakness of the UDP checksum?

Correct. A single bit flip is almost always detected, but two complementary errors can yield an unchanged sum. The checksum is simple and cheap, but far from foolproof.
