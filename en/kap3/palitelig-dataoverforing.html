Chapter 3 · The Transport Layer

Reliable data transfer

Step by step from a perfect channel to a realistic world with bit errors, loss, and delay — and the protocols that master them.

00 · The problem

Reliable over unreliable

Applications want a reliable channel. The network gives them anything but. The transport layer's job is to bridge the gap between dream and reality.

Imagine two processes communicating. The application sees it like this: data is sent into a magic pipe on one side and comes out, unchanged and in the correct order, on the other. No loss, no errors, no delay. That is an abstraction — a service that the transport layer offers upward.

But beneath this abstraction's surface lies reality: a network that can flip bits, lose packets, and deliver things out of order. The complexity of the protocol we need depends directly on how badly the underlying channel behaves.

Core principle

Sender and receiver do not know each other's state — they have no idea whether the other has received anything at all, unless they explicitly communicate it via messages. That is why we need a protocol.

The interfaces — four functions

No matter how complex the protocol becomes, we always use the same four interfaces:

FunctionRole
rdt_send()Called from the application above. Hands over data to be sent reliably.
udt_send()Called by the protocol to send a packet over the unreliable channel.
rdt_rcv()Called when a packet arrives at the receiver side from the unreliable channel.
deliver_data()Called by the protocol to deliver data up to the receiver application.

Now we build up the protocol step by step — from the trivial to the realistic. Each step adds one new complication, and we see exactly what is required to handle it.

01 · rdt 1.0

Perfect channel — trivial

The starting point: a channel that never makes errors. The protocol does not need to do anything special.

We start with the simplest model: the underlying channel is perfect. No bit errors, no packet loss. In this utopia, the protocol is trivial.

Sender (rdt 1.0)

Receives data from the application (rdt_send). Creates a packet (make_pkt). Sends it down (udt_send). Done.

Receiver (rdt 1.0)

Receives the packet (rdt_rcv). Extracts the data (extract). Delivers it up (deliver_data). Done.

The point of rdt 1.0 is not that it is useful — it is that it establishes the baseline. Everything that follows is about what happens when we remove the assumption of a perfect channel.

02 · rdt 2.0

Bit errors — ACK and NAK

The channel can now flip bits in packets. We need a mechanism for the receiver to say "got it" or "didn't get it."

Imagine dictating a text over the phone. After each word, the listener says either "OK" or "repeat that." That is exactly what rdt 2.0 does: the receiver uses a checksum to detect bit errors, and responds with ACK (all good) or NAK (error detected — resend).

New mechanisms in rdt 2.0

Error detection: Checksum in each packet lets the receiver detect corrupt data.
Feedback: ACK and NAK from receiver to sender.
Retransmission: Upon NAK, the sender retransmits the packet.

The protocol is stop-and-wait: the sender sends one packet and then waits for a response from the receiver before sending the next.

Fatal flaw in rdt 2.0

What happens if the ACK/NAK itself becomes corrupt? The sender does not know whether the receiver got the packet or not. Simply retransmitting can create duplicates that the receiver cannot distinguish from new data. rdt 2.0 is broken.

Check your understanding

What is the fundamental problem with rdt 2.0?

Correct. If the ACK/NAK itself is corrupt, the sender is in an impossible situation: retransmission may create duplicates, but proceeding may mean lost data. The solution is sequence numbers.
03 · rdt 2.1

Sequence numbers — handling duplicates

The solution to the fatal flaw: add a sequence number so the receiver can recognize and discard duplicates.

The idea is simple but powerful: the sender marks each packet with a sequence number. If the ACK/NAK is corrupt, the sender retransmits regardless. The receiver checks the sequence number — if it is the one she expects, she delivers the data up. If it is a duplicate, she silently discards it and re-sends the ACK.

Key observation

For stop-and-wait, we need only two sequence numbers: 0 and 1. Why? Because the sender never has more than one unacknowledged packet outstanding at a time. The receiver only needs to distinguish between "the packet I'm waiting for" and "the previous packet (duplicate)."

What changed?

ComponentChange from rdt 2.0
SenderAdds seq# (0 or 1) to the packet. Upon corrupt or NAK: retransmits with same seq#. Twice as many states — must remember whether the expected seq# is 0 or 1.
ReceiverChecks seq# against expected. If correct: deliver data up, send ACK. If duplicate: discard data, send ACK anyway (the sender needs the confirmation).
04 · rdt 2.2

NAK-free — ACK only

We drop NAK entirely. Instead, the receiver always sends an ACK — but with the sequence number of the last packet she received correctly.

The idea is elegant: instead of saying "that was wrong" (NAK), the receiver says "the previous one was OK" (duplicate ACK). The effect is the same, but we eliminate an entire message type.

How it works

Receiver: Always send ACK with the sequence number of the last correctly received packet.
Sender: If the ACK's sequence number does not match what she just sent, she treats it as a NAK — retransmit.

Example: The sender sends a packet with seq=0. The receiver finds a bit error. Instead of NAK, she sends ACK(1) — meaning "the last packet I received correctly had seq# 1." The sender sees that she was expecting ACK(0) but got ACK(1) — interprets it as an error and retransmits.

TCP uses this TCP is NAK-free — it uses only ACKs with sequence numbers, just like rdt 2.2. Duplicate ACKs are the fundamental signal for loss in TCP.
Check your understanding

In rdt 2.2, what does the receiver do when she receives a corrupt packet?

Correct. Instead of NAK, the receiver sends an ACK for the previous packet. The sender sees that it is not the ACK for the packet she just sent and retransmits.
05 · rdt 3.0

Loss and timeout — the complete protocol

The underlying channel can now also lose packets entirely — both data packets and ACKs. Checksums and sequence numbers alone are not enough.

With bit errors and duplicate handling in place, one major challenge remains: packets can vanish without a trace. The sender sends a packet, and simply never receives a response. Without a new mechanism, the sender would wait forever.

Solution: countdown timer

The sender starts a timer after sending a packet. If the ACK does not arrive within a "reasonable" time, the sender assumes the packet (or the ACK) was lost and retransmits.

But what if the packet was just delayed, not lost? Then the retransmission will create a duplicate — but that is fine! The sequence numbers from rdt 2.1/2.2 let the receiver recognize and discard duplicates. The receiver simply sends an ACK with the correct sequence number.

Four scenarios

rdt 3.0 handles all of these situations correctly:

rdt 3.0 is correct, but...

rdt 3.0 — also called the alternating-bit protocol — is a functionally correct protocol for reliable transfer over a channel with bit errors and loss. But it is catastrophically slow. We will see why in the next section.

Check your understanding

What happens in rdt 3.0 if the sender times out but the packet was only delayed (not lost)?

Correct. The sequence numbers save us: the receiver recognizes the duplicate and discards it. The ACK is re-sent, and the sender moves on. A bit of bandwidth waste, but no errors.
06 · Utilization analysis

Stop-and-wait is terrible

rdt 3.0 is correct. It is also so slow that it wastes nearly all available bandwidth.

Let us compute a realistic example: a 1 Gbps link with 15 ms delay in each direction (30 ms RTT), and packets of 8000 bits.

Computation

Dtrans = L/R = 8000 bit / 109 bit/s = 8 μs

Usender = L/R ÷ (RTT + L/R)
            = 0.008 ms / 30.008 ms
            = 0.00027 = 0.027 %

The sender uses only 0.027% of the link's capacity. The rest of the time — 99.97% — she sits waiting for an ACK. A gigabit link behaves like a 267 kbps link. The protocol is the dominant bottleneck, not the network.

07 · Pipelining

Fill the pipe — send multiple packets

The solution to the stop-and-wait problem: let the sender send multiple packets without waiting for an ACK for the previous one.

Pipelining is conceptually simple: instead of waiting for an ACK after each packet, we send multiple packets before any ACK has come back. Just like an assembly line — we continuously push new items in, instead of waiting for the first to finish before starting the next.

Consequences of pipelining

1. We need a larger range of sequence numbers — two (0 and 1) are no longer enough.
2. The sender and/or receiver need buffers to keep track of packets that have been sent but not acknowledged, or received but not delivered.
3. We need new rules for how to handle loss and retransmission when many packets are "in flight" simultaneously.

The effect

If we send 3 packets in a pipeline instead of 1:

Improvement

Usender = 3 × L/R ÷ (RTT + L/R)
            = 0.024 ms / 30.008 ms
            = 0.00081 = 0.081 %

Triple the utilization with just 3 packets in the pipeline! With a larger window we approach 100% utilization.

Two fundamentally different approaches to pipelining have emerged: Go-Back-N and Selective Repeat. They make different trade-offs between simplicity and efficiency.

Check your understanding

Why does pipelining need more than two sequence numbers (0 and 1)?

Correct. With stop-and-wait there is always only one outstanding packet, so 0/1 is enough. With pipelining there can be many unacknowledged packets, and each needs a unique sequence number to be identified.
08 · Go-Back-N

Cumulative ACK and the window

Go-Back-N (GBN) is the simplest pipelining protocol: the receiver buffers nothing, and the sender goes back and retransmits everything from where things went wrong.

In GBN, the sender has a window of size N: she is allowed to have up to N packets "in flight" (sent but not acknowledged) at a time. The window slides forward as ACKs arrive. The receiver is simple — she accepts only packets in the correct order.

Key rules

PropertyGBN rule
ACK typeCumulative: ACK(n) acknowledges all packets up to and including n.
TimerOne timer for the oldest unacknowledged packet.
TimeoutUpon timeout: retransmit all packets in the window — from the oldest unacknowledged onward.
ReceiverAccepts only the next expected sequence number. Everything else is discarded. Sends ACK for the last correct one.
Drawback of GBN

A single lost packet can cause many correctly received packets to be discarded and retransmitted. With a large window (e.g., N=1000), a single loss can trigger retransmission of hundreds of packets — an enormous waste of bandwidth.

Check your understanding

In Go-Back-N with window size N=4, what does the receiver do when she receives pkt5 but is expecting pkt3?

Correct. In GBN, the receiver accepts only the next expected packet. Everything else is discarded, and she re-ACKs the last in-order packet. Simple for the receiver, but wasteful of bandwidth.
09 · Selective Repeat

Individual ACK and buffering

Selective Repeat (SR) avoids unnecessary retransmission: the receiver buffers out-of-order packets and the sender retransmits only the single packet that was actually lost.

GBN discards everything that arrives out of order. That is simple, but in a network with low loss rates it is enormously wasteful. Selective Repeat takes a different approach: the receiver buffers packets that arrive out of order, and sends individual ACKs for each packet she receives correctly — regardless of order.

Key differences from GBN

PropertyGo-Back-NSelective Repeat
ACK typeCumulativeIndividual per packet
TimerOne for oldestOne per unACK'd packet
Receiver bufferNo — discard out-of-orderYes — buffer out-of-order
RetransmissionEverything from the loss pointOnly the lost one
ComplexityLowHigher

Sender and receiver rules

SR sender

Data from above: If the next seq# is within the window, send the packet and start a timer for it.
Timeout(n): Retransmit only packet n, restart its timer.
ACK(n): Mark packet n as received. If n is the oldest unacknowledged, slide the window forward to the next unacknowledged.

SR receiver

Packet n in [rcvbase, rcvbase+N-1]: Send ACK(n). If out of order: buffer. If in-order: deliver all contiguous buffered packets up, slide the window.
Packet n in [rcvbase-N, rcvbase-1]: Send ACK(n) anyway — the sender may need the confirmation.
Otherwise: Ignore.

The SR dilemma: sequence number space and window size

Selective Repeat has a subtle trap: if the sequence number space is too small relative to the window size, the receiver cannot distinguish between a new packet and a retransmission of an old one.

Example of the dilemma

Sequence numbers: 0, 1, 2, 3 (4 possible). Window size: 3.
Scenario A: Sender sends pkt0, pkt1, pkt2. All ACKs arrive. Sender sends pkt3, pkt0 (new data), pkt1. All is well — the receiver knows the new pkt0 is new data.
Scenario B: Sender sends pkt0, pkt1, pkt2. All three ACKs are lost. Sender times out and resends pkt0. The receiver has already received pkt0, pkt1, pkt2 and is now expecting pkt3 — but she sees pkt0 arrive and thinks it is new data with seq# 0.

The receiver cannot tell the difference! Her behavior is identical in both scenarios.

The rule for window size

To avoid this dilemma, the window size N must satisfy:
Selective Repeat: N ≤ 2k-1 (where k = number of bits in the seq# field)
Go-Back-N: N ≤ 2k - 1

Check your understanding

What is the most important difference between Go-Back-N and Selective Repeat when a packet is lost?

Correct. GBN "goes back" to where the error occurred and resends everything (hence the name). SR is selective — it sends only the single lost packet, because the receiver buffers the rest. SR saves bandwidth but requires more complexity at the receiver.

This section has built up the entire conceptual foundation for reliable transfer. Every principle we have seen — sequence numbers, ACKs, timers, cumulative acknowledgements, windows, pipelining — reappears in TCP. The difference is that TCP combines all of these mechanisms in a single protocol, adapted to the real world's needs.
