00 · Motivation

What TCP actually promises you

The IP layer beneath TCP is unreliable. Packets disappear, arrive out of order, get duplicated. TCP's job is to hide all of this and give the application an illusion of a perfect pipeline.

Imagine sending a letter through a postal system that sometimes loses envelopes, sometimes delivers them in the wrong order, and sometimes makes copies of the same letter without telling you. If you want the recipient to get your text in the right order, complete, and without duplicates — then you must build a system around the postal system. You must number the pages, you must request receipts, you must resend what does not arrive.

That is exactly what TCP does on top of IP. IP is the postal system that guarantees nothing. TCP is the protocol that sits on top and builds a reliable, ordered byte stream from the building blocks IP gives it.

★ Central insight

TCP is not one idea — it is a stack of solutions to a series of concrete problems that arise when you try to be reliable on top of an unreliable network. Every field in the header, every state in the protocol, is the answer to a question that had to be answered.

What TCP guarantees

From an application perspective, TCP offers four things that UDP does not give you:

  • RELIABLE No bytes are lost. What is sent, arrives.
  • IN ORDER Bytes are delivered to the application in the same order they were sent.
  • FLOW-CONTROLLED The sender does not overwhelm the receiver's buffer.
  • CONNECTION-ORIENTED Both parties agree to talk before data flows.

Note that TCP is a byte stream without message boundaries. If the application writes "Hello" and then "World" to a TCP socket, TCP may choose to send them in one packet, two packets, or split them at an entirely different point. The receiver gets only a stream of bytes — no markers for where "Hello" ended and "World" began. If you need message boundaries, your application must add them itself.

01 · Segment structure

The anatomy of a segment

Every TCP segment is a small envelope with a standardized set of fields in front of the actual data payload. Each field is the answer to a concrete problem.

Why does each field exist?

FieldThe problem it solves
Source / Dest PortThe IP address identifies the machine, but which application on the machine? Port numbers make multiplexing/demultiplexing possible.
Sequence NumberWhere in the byte stream does this payload begin? Necessary to detect loss, duplication, and ordering errors.
ACK NumberWhich byte do I expect next? Lets the sender know what has arrived (cumulative ACK).
Receive Window (rwnd)How much space do I have left in my receive buffer? The foundation for flow control.
Flags (SYN, FIN, ACK…)Control messages to open, close, and acknowledge connections.
ChecksumDetects bit errors in the header or data — IP provides no such guarantee.
HLen (Data offset)How long is the header? Needed because the options field is variable.
The missing field Notice what is not present: a "Payload Length" field. The TCP header does not tell you how much data the segment contains. Instead, the OS derives it by subtraction: Payload = Total IP Length − IP Header − TCP Header. The length comes from the layer below.

MSS — the maximum segment size

MSS (Maximum Segment Size) is the largest amount of application data that can be placed in a single TCP segment. On a typical Ethernet network, the MTU is 1500 bytes, and when you subtract 20 bytes for the IP header and 20 bytes for the TCP header, you are left with 1460 bytes as the typical MSS. Why care? Because if TCP creates segments larger than what the IP layer can handle without fragmentation, routers must split up packets in transit — and that is both slow and fragile. MSS is negotiated during the initial handshake precisely to avoid this.

Check your understanding

If the MTU on a link is 1500 bytes and you are using IPv4 + standard TCP, what is the typical MSS?

Correct: 1500 − 20 (IP header) − 20 (TCP header) = 1460 bytes. If the headers had options, MSS would be even smaller.
02 · Sequence numbers and ACK

How TCP counts bytes

Sequence numbers are at the core of all reliability. Misunderstand this and the rest of TCP makes no sense.

The most common misconception is thinking that the sequence number numbers segments — segment 1, segment 2, segment 3. It does not. The sequence number is a pointer into a byte stream. If the sender writes 1000 bytes into its socket and TCP chooses to split them into two segments of 500 bytes each, then the first segment gets seq=0 (or whatever the starting number is) and the second segment gets seq=500 — because the second segment contains bytes 500 through 999.

The ACK number follows the same logic, but from the receiver's side: "the next byte I expect to see is this one." If the receiver has gotten all bytes up to 999, she sends ACK=1000. This is a cumulative ACK — it acknowledges not just the last packet, but everything up to byte 1000.

★ Why cumulative ACKs?

If an ACK is lost in transit, it is not a catastrophe — the next ACK overrides it anyway. ACK=1000 tells the sender that everything before byte 1000 has arrived safely, even if the previous ACK=500 never made it. This provides robustness without extra work.

03 · RTT and timeout

How long should we wait?

If a segment is lost, the sender must retransmit it. But how long should she wait before deciding it is lost?

This is a surprisingly delicate question. Wait too short, and you retransmit unnecessarily — you worsen the already stressed situation and load the network. Wait too long, and your application feels slow and unusable on lossy connections. The right answer is "a little more than typical RTT," but what is typical RTT on a network where latency jumps up and down?

⚠ The problem

RTT varies from moment to moment. A single measurement can be atypical — a random spike, or an unusually fast round. If we set the timeout based on the last measurement alone, it becomes wildly unstable.

✓ The solution: EWMA

We smooth out the measurements with an exponentially weighted moving average. Each new measurement influences the estimate slightly — old measurements lose influence exponentially fast.

EstimatedRTT = (1 − α) × EstimatedRTT + α × SampleRTT

With α = 0.125, each new measurement contributes 12.5% to the estimate. The estimate fluctuates much less than the raw data, but still responds to real changes in the network.

Safety margin: DevRTT

But EstimatedRTT alone is not enough. If we set Timeout = EstimatedRTT, half of the measurements would lie above and half below — we would get false timeouts all the time. We need a safety margin, and the margin should be larger when RTT fluctuates a lot.

The solution is to estimate the variance — how much SampleRTT typically deviates from the estimate:

DevRTT = (1 − β) × DevRTT + β × |SampleRTT − EstimatedRTT|

And then TCP gets its final timeout formula:

TimeoutInterval = EstimatedRTT + 4 × DevRTT

The factor 4 is not magic — it is a practically chosen value that gives a generous margin without being absurdly large. When RTT is stable, DevRTT becomes small and the timeout sits close above EstimatedRTT. When RTT starts fluctuating, DevRTT grows and the timeout expands automatically.

04 · Sender logic

One timer per connection

The naive intuition says: one timer per packet. That is wrong — and for a good reason.

If you think about it logically, it seems sensible that each individual packet should have its own timer. If you send three packets, you start three stopwatches, and if one of them expires you know exactly which packet to retransmit. Clear, tidy, intuitive.

⚠ Why it does not work in practice

A busy server may have 10,000 open connections, each with thousands of packets in flight. That means millions of active timer objects. Just waking the process to check each of them would choke the CPU. It does not scale.

✓ TCP's design

Standard TCP implementations use a single retransmission timer per connection. It tracks the oldest unacknowledged packet — SendBase. When an ACK arrives that moves SendBase forward, the timer is restarted (if there are still unacknowledged packets). If the timer expires, the oldest unacknowledged packet is retransmitted.

The sender's three events

The sender reacts to three things, and only three things:

  1. 01 · Data from the application. Create a new segment with seq = NextSeqNum, send it to the IP layer, update NextSeqNum. If the timer is not already running, start it.
  2. 02 · Timeout. Retransmit the oldest unacknowledged segment. Restart the timer.
  3. 03 · ACK received with value y. If y > SendBase, then something new has been acknowledged — move SendBase to y. If there are still unacknowledged segments, restart the timer; otherwise stop it.
SendBase and NextSeqNum Think of the sender's window as a sliding box: SendBase is the left edge (oldest unacknowledged byte), NextSeqNum is the right edge (next byte to be sent). Everything between them is "in flight" — sent but not yet acknowledged.

The third situation is the beautiful one: even though an ACK is lost in transit, the next ACK saves everything — because ACKs are cumulative. The sender does not need to retransmit anything at all. Losing an isolated ACK costs nothing, as long as a later ACK arrives before the timeout.

The second situation — premature timeout — is more interesting. The sender gets impatient and retransmits the first packet before the ACK made it back. A bit of bandwidth waste, but no errors.

06 · Fast retransmit

Don't wait for the timeout

Timeouts are conservative — they are typically set to hundreds of milliseconds. If we have a clear hint that a packet is lost, why not act on it immediately?

The receiver's rule for ACK generation, defined in RFC 5681, is simple: if a segment arrives out of order — that is, with a higher sequence number than expected — the receiver should immediately send a duplicate ACK that repeats the number of the byte she is still waiting for. Each segment that arrives after the gap will produce another duplicate ACK with the same number.

The sender seeing this thinks: "Why am I getting the same ACK over and over? That must mean newer segments are arriving, but something old is missing." That is a strong indication of loss — stronger than just waiting for a timeout.

★ The rule of thumb: three duplicate ACKs

If the sender receives three duplicate ACKs in a row for the same byte, she retransmits the missing segment immediately — without waiting for the timer to expire. This is called fast retransmit.

Why exactly three?

That is a good question. Why not one? Or five? The answer lies in the fact that duplicate ACKs do not always mean loss. The network can also reorder packets — packet 5 can arrive before packet 4 even though both were sent correctly. If we acted on the first duplicate ACK, we would often retransmit completely unnecessarily, because the missing packet is on its way and was just slightly delayed.

Three duplicate ACKs is an empirically chosen balance: enough that reordering is probably not the explanation, but not so many that we lose too much time before acting. It is a constant that has stood the test of more than 20 years of experience with TCP implementations.

Check your understanding

Why doesn't TCP wait for just one duplicate ACK before retransmitting?

Correct. Packet reordering is common enough that a single duplicate ACK is not strong enough evidence of loss. Three in a row is a much more convincing signal.
07 · Flow control

Don't drown the receiver

TCP is reliable on behalf of the network — but it must also protect the receiver from itself. What if the sender is faster than the application reading the data?

Imagine a server streaming data into a receiver's TCP buffer much faster than the application can read from it. The buffer grows. Eventually it is full — and the next segment that arrives has no place to go. It gets dropped, must be retransmitted, and the whole situation gets worse. TCP solves this by having the receiver constantly tell the sender exactly how much space she has left.

✓ Receive Window (rwnd)

In every single ACK, the receiver tells the sender how many free bytes she has in her receive buffer — the value is placed in the Receive Window field in the header. The sender commits to never having more than rwnd bytes "in flight" (sent but not acknowledged) at the same time.

The result is a kind of rhythm: the sender sends data, the receiver's application reads data, and rwnd grows and shrinks in sync. If the application suddenly stops reading, rwnd rapidly shrinks toward zero and the sender pauses automatically. When the application wakes up and reads again, rwnd grows and the sender is allowed to continue.

The 16-bit bottleneck

The original rwnd field is only 16 bits — a maximum of 65,535 bytes, or 64 KB. On a fast modern network, this is far too little. If you have a 1 Gbps line with 100 ms ping, you can only have 64 KB in flight before you must wait for an ACK. The result is that the link sits idle most of the time. This is called the "long fat networks" problem.

The solution is TCP Window Scale — an option negotiated during the initial handshake. It lets both sides agree on a multiplier (a bit shift of up to 14 bits). With maximum scaling, rwnd can represent up to approximately 1 GB. That is enough to fill even extremely fast and high-latency links.

Negotiated only in SYN The Window Scale factor is negotiated exclusively in the SYN packets during the initial handshake. This means that if your SYN packet does not include the option, neither party can use scaled windows for the rest of the connection — it is now or never.
Check your understanding

What is the difference between flow control and congestion control?

Correct. Flow control is an agreement between one sender and one receiver. Congestion control is an agreement between all senders and the shared network. They solve two different problems and use different signals.
08 · Connection establishment

The three-way handshake

Before any data can flow, the two parties must agree that they are going to talk — and agree on parameters like starting sequence numbers. Why do we need three messages for something so simple?

The naive solution is a two-way handshake: the client says "let's talk," the server replies "OK." Clear, simple — and unfortunately broken. The problem is that messages can be delayed arbitrarily long in the network, and old messages can show up long after the client has given up and moved on.

⚠ Half-open connections

Imagine the client sends req_conn(x), but never gets a response. She gives up and closes. Meanwhile, req_conn(x) was just delayed in the network — it finally arrives at the server, which happily opens a connection and waits for data. The client is gone. The server has a half-open connection that will never be used — and potentially many of them, if this happens often. This is a real vulnerability (SYN flooding attacks exploit exactly this).

⚠ Duplicate old data

Worse: an old req_conn(x) combined with old data(x+1) packets from a terminated connection can be mistaken for the start of a new session — and the data gets accepted as if it belonged. This is not theoretical; it is a real way protocols have failed.

✓ Three ways solve it

In a three-way handshake, both parties choose a random starting sequence number (x and y). The client must then confirm the server's y in a third message before the connection is considered established. This means the server does not open a connection in earnest until she has proof that the client actually exists and is actively ready — not just a ghost from the past.

The dance itself

Note that the final ACK message can carry data — it does not have to be empty. This is an optimization: if the client already knows what she wants to say (for example, an HTTP request), she can pack it into the third handshake message and save a round trip.

09 · Closing the connection

A polite goodbye

Closing a connection is not trivial either — both sides may have more data to send, and the final message can get lost.

When one of the parties is done, she sends a segment with the FIN flag set. The other side replies with an ACK. But only one direction is closed — TCP is full duplex, so the other side can still have more to say. When that side is also done, she sends her own FIN, and the first party replies with an ACK.

Four messages total — although FIN and ACK from the same side can be combined into a single segment. The client who initiates the close enters a special TIME_WAIT state after her final ACK, where she stays for typically 30 seconds to 2 minutes (2 × MSL — Maximum Segment Lifetime). Why? Because the final ACK may have been lost. If it was, the server will retransmit her FIN, and the client must still be around to reply. Only after the timeout expires does the client actually get to forget the connection entirely.

❋ ❋ ❋

The big picture

We have gone through segment structure, sequence numbers, RTT estimation, retransmission logic, fast retransmit, flow control, and connection establishment and termination. Everything is interconnected: each mechanism exists because a previous mechanism would have failed without it. Sequence numbers make ACKs meaningful. Cumulative ACKs make lost ACKs survivable. RTT estimation makes timeouts robust. A single timer per connection makes the protocol scalable. The three-way handshake makes connections safe against ghosts from the past.
