00 · Motivation

Why congestion control?

Flow control protects one receiver. Congestion control protects the shared network between all senders.

Imagine a motorway where each driver decides their own speed. Without any form of regulation — traffic lights, speed limits, on-ramps — the road will eventually gridlock. Congestion control in TCP is the traffic light: a mechanism that lets the sender adjust her speed based on how full the network appears to be, without any central authority managing it.

Two windows, one constraint

The TCP sender is governed by two windows that both impose constraints:

WindowWhat it protects
rwndReceive window — set by the receiver in the TCP header. Protects the receiver's buffer from overflow.
cwndCongestion window — maintained by the sender locally, invisible in the header. Protects the network from overload.

The rule is simple:

The sender's law

LastByteSent − LastByteAcked ≤ min(cwnd, rwnd)

The sender can never have more data "in flight" than the smaller of the two windows. In practice, when the network is the bottleneck, cwnd < rwnd, and it is cwnd that governs.

TCP's sending rate then becomes approximately:

Sending rate

rate ≈ cwnd / RTT  bytes/sec

cwnd is invisible Note that rwnd is advertised in the TCP header and can be observed in a packet capture. cwnd, on the other hand, exists only internally at the sender — it is never visible on the wire.

The bottleneck link

When TCP increases the sending rate, eventually one link in the path becomes saturated — the bottleneck link. The router's output queue fills up, and packets begin to be dropped. The key insight:

Two insights about the bottleneck

1. Increasing the sending rate beyond the bottleneck capacity does not give higher throughput — it only gives more packet loss.

2. Increasing the sending rate beyond the bottleneck capacity increases RTT, because packets wait longer in the queue.

The goal: "Keep the end-to-end pipe just full, but not fuller."

Two approaches to congestion control

There are two fundamentally different ways to attack the congestion problem:

ApproachHow it works
End-to-endThe network provides no explicit feedback about congestion. The sender must infer the state on her own — based on observed loss (timeout or duplicate ACKs) and delay. TCP uses this approach.
Network-assistedRouters provide explicit feedback to the sender about congestion levels — for example via special control messages, or by setting bits in the packet header that signal a link is approaching congestion.

The Internet's TCP has traditionally been purely end-to-end: the IP layer provides no help, and the sender is left to her own devices. All information about the network's state must be inferred indirectly — from ACKs that fail to arrive, from delays that increase, or from packets that vanish. This is precisely what makes TCP congestion control such an elegant and challenging problem.

01 · Slow start

Exponential ramp-up

The name is misleading — slow start is actually the fastest phase of TCP. The window doubles every RTT.

When a TCP connection has just been established, the sender knows nothing about the network's capacity. Sending too much immediately could cause congestion. Sending too little wastes time. The solution is to start cautiously and double the sending rate every RTT until a limit is hit.

The mechanism

The slow start algorithm

1. Start with cwnd = 1 MSS.
2. For each received ACK, increase cwnd by 1 MSS: cwnd = cwnd + MSS.
3. The effect: cwnd doubles per RTT (exponential growth).

Example

With MSS = 1500 bytes and RTT = 200 ms:

RTTcwndSegments sent
01 MSS1
12 MSS2
24 MSS4
38 MSS8
416 MSS16

Initial rate: 1500 / 0.2 = 7.5 kB/s. After 4 RTTs: 24,000 / 0.2 = 120 kB/s. Exponential growth quickly ramps up to available capacity.

When does slow start end?

Slow start terminates upon one of three events:

  • Timeout — cwnd is reset to 1 MSS, ssthresh = cwnd/2, and slow start restarts.
  • cwnd ≥ ssthresh — transition to congestion avoidance (linear growth).
  • 3 duplicate ACKs — transition to fast recovery.
ssthresh ssthresh (slow start threshold) is a variable that remembers approximately where things went wrong last time. It typically starts at a high value (e.g., 64 KB) and is halved on each loss. It marks the boundary between exponential and linear growth.
Check your understanding

During slow start with cwnd = 4 MSS, TCP sends 4 segments and receives 4 ACKs. What is the new cwnd?

Correct. In slow start, cwnd increases by 1 MSS for each ACK. With 4 ACKs: 4 + 4 = 8 MSS. Cwnd doubles per RTT.
02 · Congestion avoidance

Additive increase, multiplicative decrease

When cwnd has reached ssthresh, TCP shifts from exponential to cautious linear growth — and cuts brutally on loss.

AIMD (Additive Increase, Multiplicative Decrease) is the core of TCP's congestion control. The idea is beautiful in its asymmetry: grow slowly upward, cut rapidly downward. This asymmetry provides stability and fairness — properties that pure exponential growth could never deliver.

Additive increase

In the congestion avoidance phase, cwnd increases by 1 MSS per RTT — not per ACK as in slow start. The formula per ACK is:

Congestion avoidance — per ACK

cwnd = cwnd + MSS × (MSS / cwnd)

Since approximately cwnd/MSS ACKs arrive per RTT, this gives a total increase of 1 MSS per RTT — linear growth.

Multiplicative decrease

Upon packet loss, TCP halves the window:

Upon loss

ssthresh = cwnd / 2
cwnd = ssthresh  (upon 3 dup-ACKs, TCP Reno)
cwnd = 1 MSS  (upon timeout, all variants)

The sawtooth pattern

The result is the characteristic sawtooth pattern: cwnd grows linearly upward, drops sharply on loss, grows linearly again. TCP continuously "probes" for more bandwidth.

Worked example: congestion avoidance

Example

Assume cwnd = 3000 bytes and MSS = 1500 bytes. That means 2 segments in flight, hence 2 ACKs per RTT.

ACK 1: cwnd = 3000 + 1500×(1500/3000) = 3750
ACK 2: cwnd = 3750 + 1500×(1500/3750) = 4350

Net increase over the entire RTT: approximately 1 MSS (from 3000 to ~4500). Linear growth, as expected.

Check your understanding

In congestion avoidance with cwnd = 10 MSS, how much does cwnd grow in one RTT?

Correct. In congestion avoidance, growth is always 1 MSS per RTT, regardless of cwnd size. That is precisely what makes it linear.
03 · Fast recovery

Reno vs. Tahoe

Not all packet losses are equally severe. Three duplicate ACKs mean that something is still getting through — and TCP can react more mildly.

There is an important difference between a timeout and three duplicate ACKs. A timeout means: "I haven't heard anything at all for a long time — the network might be completely down." Three duplicate ACKs mean: "One segment was lost, but other segments are getting through — because the receiver is sending ACKs." TCP Reno exploits this difference.

TCP Tahoe (the original)

TCP Tahoe (1988) treats all losses the same:

Tahoe — upon any loss

ssthresh = cwnd / 2
cwnd = 1 MSS
Restart slow start

TCP Reno (the improvement)

TCP Reno (1990) differentiates:

Reno — upon 3 duplicate ACKs

ssthresh = cwnd / 2
cwnd = ssthresh + 3 MSS
Enter fast recovery

Reno — upon timeout

ssthresh = cwnd / 2
cwnd = 1 MSS
Restart slow start

What happens in fast recovery?

During fast recovery, cwnd increases by 1 MSS for each duplicate ACK that arrives (these indicate that subsequent segments are getting through). When a new ACK arrives (acknowledging the retransmitted segment), fast recovery ends:

New ACK in fast recovery

cwnd = ssthresh
Enter congestion avoidance

Comparison

EventTCP TahoeTCP Reno
Timeoutcwnd → 1 MSS, slow startcwnd → 1 MSS, slow start
3 dup-ACKscwnd → 1 MSS, slow startcwnd → ssthresh+3, fast recovery

Reno avoids the costly trip back to 1 MSS upon duplicate ACKs — which can save many RTTs of low throughput.

Check your understanding

TCP Reno detects 3 duplicate ACKs while cwnd = 20 MSS. What happens?

Correct. ssthresh = 20/2 = 10. cwnd = ssthresh + 3 = 13 MSS. Reno enters fast recovery instead of slow start.
04 · TCP CUBIC

Faster recovery with a cubic function

AIMD is fair, but slow. CUBIC uses a smarter curve to exploit capacity faster.

Classic TCP uses AIMD: linear increase of 1 MSS per RTT. On a link with high capacity and long delay, it can take many RTTs to fill the link after a loss. CUBIC asks the question: can we do better?

The insight

The CUBIC principle

Let Wmax be the sending rate when the last loss occurred. After a loss, we know the network probably has not changed much. Then it is safe to quickly approach Wmax again — but we should be cautious near Wmax, because that is where things went wrong last time.

Cubic growth

CUBIC increases cwnd as a function of time since the last loss, not of RTT:

  • Far from Wmax — large, rapid increases (the curve is steep).
  • Near Wmax — cautious, small increases (the curve flattens out).
  • Beyond Wmax — cautiously probes for new capacity (the curve rises again).

The point K is the time at which cwnd would reach Wmax. K is tunable. The curve is symmetric around K — it resembles a cubic function (hence the name).

Default in Linux TCP CUBIC is the default congestion control algorithm in Linux and is the most widely used variant among popular web servers today.
Check your understanding

What is the main advantage of CUBIC over classic AIMD?

Correct. CUBIC combines aggressive growth (far from Wmax) with caution (near Wmax), and thus exploits capacity more efficiently than pure linear AIMD.
05 · Fairness

Is TCP fair?

If K TCP sessions share a bottleneck with capacity R, each should ideally get R/K.

Fairness is not just an academic question — it concerns the fundamental functioning of the Internet. If one connection could take everything, all others would starve. AIMD has an elegant property: under idealized conditions, parallel TCP connections converge toward equal allocation.

AIMD convergence

Consider two TCP sessions sharing a bottleneck with capacity R. Plot the throughput of session 1 on the x-axis and session 2 on the y-axis:

A → B: both sessions increase additively (slope 45°) until they hit the capacity boundary.
B → C: both halve cwnd (pull toward origin), but this moves the point closer to the green line.
Repeat — the point converges toward equal allocation.

The assumptions

Fairness holds under idealized assumptions

Same RTT — connections with lower RTT increase faster and get more bandwidth in practice.
Fixed number of sessions — in reality, connections come and go.
Only congestion avoidance — the proof assumes linear growth, not slow start.

Fairness and UDP

UDP applications (e.g., video streaming) do not participate in congestion control. They can send as fast as they want and thereby take more than their "fair" share. There is no "Internet police" enforcing fairness.

Parallel TCP connections

A browser that opens 10 parallel TCP connections to a server effectively gets 10 × its fair share compared to an application using one connection. This is a "legal" way to cheat — and it is widespread.

06 · Evolution

From Tahoe to QUIC

TCP has evolved for 40 years. The most recent evolution moves transport functionality up to the application layer.

TCP and UDP have been the two transport protocols for over four decades. During that time, TCP has been improved repeatedly — from Tahoe via Reno to CUBIC. But the most radical change is an entirely new approach: QUIC, which builds transport functionality on top of UDP.

TCP's evolution

YearMilestone
1981RFC 793 — original TCP specification
1988TCP Tahoe — slow start and congestion avoidance (Jacobson)
1990TCP Reno — fast retransmit and fast recovery
2005BIC TCP
2008TCP CUBIC — cubic growth function, default in Linux since 2006 (RFC 8312 published 2018)

Different scenarios, different challenges

ScenarioChallenge
Large transfersMany packets "in flight"; one loss stalls the entire pipeline
WirelessLoss due to noise is confused with congestion — TCP reduces unnecessarily
Long delaysExtremely long RTT makes AIMD ramp-up painful
Data centersLatency-critical services where even milliseconds of queuing delay matter

QUIC: Quick UDP Internet Connections

QUIC is an application-layer protocol built on top of UDP. It implements reliability, congestion control, encryption, and multiplexing — all in user space, without waiting for OS updates.

QUIC's advantages

PropertyAdvantage over TCP
1-RTT handshakeTCP + TLS requires 2 serial handshakes. QUIC does everything in one RTT — reliability, congestion control, authentication, and encryption.
Per-stream reliabilityTCP has head-of-line (HOL) blocking: one lost segment blocks all data behind it. QUIC multiplexes multiple streams independently — loss in one stream does not block the others.
In user spaceUpdates do not require OS changes. Google rolls out improvements in Chrome without waiting for kernel changes.

QUIC and head-of-line blocking

With TCP and HTTP/2: three GET requests share one TCP connection. If a segment belonging to request 1 is lost, all three must wait for the retransmission — even though data for requests 2 and 3 has already been received.

With QUIC: each request has its own stream with independent reliable delivery. Loss in stream 1 blocks only stream 1 — streams 2 and 3 are delivered undisturbed.

Check your understanding

What is the main advantage of QUIC's per-stream reliability?

Correct. TCP's single-stream model means one lost segment blocks everything behind it. QUIC solves this with independent streams, which eliminates head-of-line blocking between requests.
